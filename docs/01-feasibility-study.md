## 一页看懂

### 这个系统能做什么

把它想成一个**带门禁的加密保险箱**：

1. **管理员**是保险箱管理员，负责创建账号、划分用户组、把文件或文字秘密放进保险箱。
2. 放进去的东西会被**锁成乱码**；即使有人直接拿到硬盘上的文件，也打不开。
3. 管理员可以指定“哪个组”或“哪个人”能取哪件东西。
4. 被授权的人登录后，才能看到并解密；没被授权的人连列表里都看不到。
5. 谁在什么时候看了、下载了什么，都会留下记录。
6. 既能在**浏览器（Web 端）**使用，也能在**安装版客户端（应用端）**使用。

### 必须提前知道的 5 个限制

1. **授权用户解密后，可以拍照、另存、转发。** 这是所有加密文件系统都挡不住的。我们能做的是：限制下载、加水印、全程留痕、及时撤销权限。不能承诺“绝对防泄露”。
2. **“文件放在本地”指的是放在运行系统的那台电脑上**，不是每个用户自己的电脑。那台电脑关机或断网，其他人就访问不了。
3. **服务器端加密不等于防住最高管理员。** 如果钥匙由服务器保管，拥有服务器最高权限的人理论上能解密。要防住这一点，需要更复杂的“端到端加密”，代价是丢了密码可能永久丢数据。
4. **加密不能代替杀毒和备份。** 勒索软件、硬盘损坏、误删，仍然要靠备份解决。
5. **“不能被直接打开”靠的是真加密，不是改后缀。** 只改文件名后缀属于“掩耳盗铃”，本方案不会这么做。

### 初步结论

**技术上可行，没有绕不过去的障碍。** 推荐先做一个“小范围、可信环境”的版本：网页端 + 桌面客户端、本地服务器、服务器端加密、小团队使用，把核心功能做扎实，再逐步扩展到云端、手机端和更强的端到端加密。

## 二、项目概述

### 2.1 一句话说明

做一个**加密文件与敏感信息管理系统**：管理员把文件、网站账号、数据库密码等内容加密保存，并按“用户组”或“单个用户”精确授权；只有被授权的人可以查看和解密，所有敏感操作可追溯。

### 2.2 为什么值得做

- 小团队常把密码、数据库连接信息、合同、证件扫描件等敏感资料放在共享盘或聊天工具里，容易被无关人员看到。
- 现有的网盘大多只做“访问控制”，文件本身没有加密；服务器或硬盘一旦泄露，内容就暴露。
- 现成的密码管理器擅长保存账号密码，但对“任意文件 + 自定义用户组 + 本地部署 + 自定义管理界面”的支持不一定合适。
- 自己做一个长期维护的开源项目，可以完全掌控数据、权限和后续迭代方向。

### 2.3 你提出的要求与本文档对应关系

| 你的要求 | 我们的理解 | 本报告对应位置 |
|---|---|---|
| Web 端和应用端两个模式 | 浏览器可访问，同时提供安装版客户端；应用端具体是电脑还是手机，需要确认 | 4.4 节、D1 |
| 管理员 / 普通用户，组与单独授权 | 管理员管理用户和组；内容按组或按人授权；权限立即生效 | 4.3 节、需求分析 |

## 三、系统边界：能解决什么，不能解决什么

### 3.1 能解决

- 敏感文件与文字秘密的**集中加密存储**。
- **按用户组或单个用户授权**，未被授权者看不到条目，也拿不到内容。
- 管理员可以**随时撤销权限**，撤销后下一次访问即失效。
- 文件在磁盘上是密文，脱离系统无法直接打开。
- 查看、解密、下载、授权变更等操作**可审计**。
- 管理员可以**备份和恢复**，降低硬盘损坏、误删带来的损失。
- 网页端和安装版客户端共享同一套账号、权限和数据。

### 3.2 不能解决（需要你知情并接受）

| 做不到的事 | 原因 | 可采取的缓解办法 |
|---|---|---|
| 阻止授权用户拍照、录屏、抄写 | 内容到了用户眼前，技术上无法完全控制 | 屏幕水印、下载留痕、最小授权、及时撤销、保密制度 |
| 阻止授权用户把解密后的文件转发给别人 | 文件一旦落到用户电脑上，就不再受系统控制 | 控制下载权限、审计、离职/离组立即撤销 |
| 防住拥有服务器最高权限的恶意管理员 | 钥匙在服务器上时，最高权限者可以取钥匙 | 采用端到端加密（后续可升级），或严格限制服务器管理员 |
| 防病毒、防勒索软件 | 加密解决的是“被看见”，不是“被破坏” | 杀毒、系统更新、离线备份、最小权限 |
| 保证 7×24 小时在线 | 本地单台电脑存在停机、断网风险 | UPS、备用机、云端部署（后续） |
| 防止弱密码被撞库 | 用户密码强度是薄弱环节 | 密码策略、登录限速、锁定、后续加双因素认证 |
| 让文件在用户自己的电脑上永远保持加密 | 用户选择“下载/另存”后，明文就离开了系统 | 默认在线查看、按需授权下载、水印和留痕 |

> **一句话总结**：这套系统能可靠地管住“在系统内部”的访问；管不住“已经离开系统”的内容。这个边界必须在需求阶段讲清楚，避免以后产生“为什么还能被转发”的误解。

## 四、技术可行性分析

### 4.1 加密技术是成熟的

- **文件加密**：使用国际通行、经过长期审查的 **AES-256-GCM** 算法。它既能把内容变成乱码，也能发现文件是否被篡改。就像给每个保险箱配一把独立钥匙，并在箱门上加防拆封条。
- **密码保存**：用户登录密码不会明文保存，而是用 **Argon2id** 这类“慢速哈希”算法处理。即使数据库泄露，攻击者也很难反推出原始密码。
- **传输加密**：浏览器/客户端与服务器之间使用 **HTTPS（TLS）**，防止同一网络里的人窃听。就像把文件装进防窥袋再传递。
- **密钥管理**：采用“信封加密”。每个文件有一把自己的小钥匙，小钥匙再用主钥匙锁起来。这样以后更换主钥匙、单独授权、迁移数据都更容易。
- **实现方式**：全部使用成熟的开源加密库，**不自创加密算法**。自创加密算法是安全项目的大忌。

**结论：加密部分没有技术障碍，关键是密钥保管和权限校验要做对。**

### 4.2 “文件不能被直接打开”如何实现

不是在文件名上动手脚，而是：

1. 文件上传后，内容用 AES-256-GCM 加密成二进制密文。
2. 密文存放在**网站无法直接访问的目录**，用随机生成的文件名保存，不保留原后缀名。
3. 原始文件名、类型等信息另行保存；下载时由系统验证权限后，再还原给合法用户。
4. 密钥与密文**分开存放**，密钥文件不放在网页目录、不写进代码、不写进日志。
5. 每次读取都校验权限和文件完整性；发现篡改就拒绝返回。

这样即使有人把整个存储目录拷走，拿到的也只是一堆无法识别的密文；用记事本、播放器、Office 等常见软件都打不开。

> 注意：如果管理员自己把文件“解密下载”到电脑上，那份下载件就是明文，不再受本系统保护。这是正常且无法避免的。

### 4.3 权限模型是可行的

采用 **RBAC（基于角色的访问控制）+ 条目级授权**：

- **角色**：管理员、普通用户。
- **用户组**：管理员创建，例如“财务组”“运维组”；一个用户可以属于多个组。
- **授权对象**：每一条内容（文件或文字）可以授权给若干个组，也可以单独授权给某个人。
- **生效规则**：组授权和个人授权取并集；只要其中一条授权成立，就可以查看。
- **校验时机**：每一次列表、查看、解密、下载请求，服务器都重新检查权限，不能只靠前端隐藏按钮。
- **撤销**：把用户移出组、停用账号或取消授权，下一次请求立即失效（不需要重新登录）。
- **管理边界**：管理员负责“管人、管组、管权限”；是否自动拥有所有内容的查看权，是一个需要你确认的安全策略（建议默认不自动拥有，见需求分析）。

潜在难点在于“组授权”的含义：把用户加入某个组，他会立刻获得该组所有已授权内容的访问权；这是预期行为，但管理员必须清楚。后续界面会提供“这个组现在能看哪些内容”的预览，降低误授权风险。

### 4.4 Web 端 + 应用端怎么做

有两种常见形态，成本和体验差别很大：

1. **网页优先 + 桌面客户端外壳**：网页和客户端使用同一套界面；客户端只是把网页“装进一个独立的窗口”，并增加安装、托盘、自动更新等能力。开发量小，更新统一。
2. **网页 + 原生手机 App**：手机 App 需要单独适配、打包、上架应用商店，Android 和 iOS 还要分别处理；成本明显更高。
3. **手机先装“网页快捷方式”（PWA）**：用手机浏览器打开并“添加到主屏幕”，体验接近 App，但不需要上架商店；功能和系统集成能力有限。

**结论：**
- 如果“应用端”指**电脑桌面软件**，推荐“网页优先 + 桌面客户端外壳”，性价比最高。
- 如果指**手机 App**，建议第一期先做手机也能用的响应式网页/PWA，原生 App 放到后续版本；否则会显著拖慢核心安全功能的进度。
- 具体选哪个，见 D1。

### 4.5 本地存储与多人访问

“文件放本地”在多人系统里有两种完全不同的含义，需要先对齐：

- **含义一（本方案默认）**：文件放在**运行服务的那台电脑/服务器**的本地磁盘上。其他用户通过浏览器或客户端，经局域网访问这台机器。这是“本地部署”，不是“每个用户各自存一份”。
- **含义二**：每个用户把文件存在自己电脑上。这样无法实现“管理员授权后其他人查看”，与需求冲突，不建议。

本方案默认按含义一设计：

- 一台主机运行服务，保存数据库和加密文件目录。
- 同一局域网内的用户，用浏览器访问主机，或安装客户端后连接主机。
- 主机需要设置固定局域网地址，并做好防火墙和 HTTPS。
- 若要在公司外访问，需要公网 IP、域名、证书或 VPN；这会引入新的安全风险，建议放到后续阶段，不放进第一版。
- 主机必须做备份；主机损坏时，系统和数据都要能恢复。

### 4.6 长期开源的可行性

技术上是可行的，但需要从第一天就按开源项目来做：

- 不把密码、密钥、真实数据写进代码仓库；提供配置样例和初始化向导。
- 所有第三方依赖选择许可证兼容的开源组件，不使用来源不明的代码。
- 提供 README、安装说明、安全说明、贡献指南和问题反馈模板。
- 建立基本的安全流程：依赖漏洞扫描、代码审查、漏洞披露渠道。
- 开源不代表“不安全”。真正安全的系统不依赖代码保密，而依赖密钥管理和正确实现。公开代码反而能让更多人审查。
- **许可证需要单独确认**：宽松许可证（如 Apache-2.0）利于传播；AGPL 要求修改后对外提供服务也必须开源。这是法律选择，建议在准备上 GitHub 前单独决策，不阻塞开发。

### 4.7 整体技术路线候选

下面三条是“整体打包”的路线，不需要你懂框架名字，只看优缺点。

#### 方案 A：Python 后端 + 网页前端 + 桌面客户端外壳（推荐）

- **像什么**：后厨（Python 服务）负责保险箱和门禁，前厅（网页界面）负责展示；桌面客户端就是把前厅装进一个独立窗口。
- **优点**：
  - 代码可读性好，安全逻辑集中，未来容易审查和维护。
  - Python 的加密、数据库、接口生态成熟，开发速度快。
  - 网页端和桌面客户端共用界面，减少重复开发。
  - 开源社区大，找人接手和贡献相对容易。
- **缺点**：
  - 需要同时掌握 Python 和前端两套技术。
  - 服务器部署和桌面打包比“纯网页”多一些步骤。
  - 桌面外壳具体用 Electron 还是 Tauri，需要在阶段 6 的 spec 里再单独选择。

#### 方案 B：全 TypeScript 路线（网页 + 后端 + Electron 桌面端）

- **像什么**：前厅、后厨、外带窗口都用同一种语言和同一套工具搭建。
- **优点**：前后端同一种语言；桌面端与网页端整合自然；开源生态活跃。
- **缺点**：Node/Electron 依赖多、体积大；安全敏感的后端同样要严格配置；对普通用户来说维护门槛不一定更低。

#### 方案 C：基于现成开源项目二次开发

- **像什么**：买一套已经装修好的房子，再改格局。可参考 Vaultwarden、Nextcloud 等。
- **优点**：基础功能成熟，上线快，安全机制经过一定验证。
- **缺点**：现有项目是围绕“密码管理”或“网盘”设计的，用户组、文件授权、界面和“本地密文目录”未必完全符合你的需求；深度定制受原项目架构和许可证限制；长期维护要跟着上游升级，容易被“绑住”。
- **结论**：如果目标是做一个**自己长期维护、可自由迭代的开源产品**，不推荐把二次开发作为主线；可以借鉴它们的做法，但从源头保持自主。

**推荐：方案 A。** 理由：核心安全逻辑清晰、开发效率高、网页与桌面端可复用、长期开源好维护。

### 4.8 加密信任模式候选

这是**本项目最重要的安全决策**，直接影响“谁理论上能解密”。

#### 模式一：服务器端加密（v1 推荐）

- **像什么**：银行保险箱的钥匙由银行保管。你出示有效证件（登录并通过权限校验），银行帮你开箱。
- **优点**：
  - 实现简单、稳定，用户忘记密码可由管理员重置。
  - 权限撤销即时生效。
  - 备份、恢复、迁移容易。
  - 能防住“硬盘被偷”“备份泄露”“网站被外部攻破后拿到数据库”等场景。
- **缺点**：服务器最高管理员理论上能拿到钥匙并解密。适合“信任服务器管理员”的小团队/家庭/公司内部。

#### 模式二：端到端加密

- **像什么**：每个用户自己带一把钥匙，服务器只负责保管上锁的箱子，连银行也打不开。
- **优点**：服务器被攻破也拿不到明文；对管理员也保密。
- **缺点**：
  - 用户忘记密码或丢失钥匙，数据可能**永久无法恢复**。
  - 管理员授权、撤销、把用户加入组，都涉及复杂的密钥重新封装。
  - 开发难度和出错风险明显更高；用户操作也更复杂。
  - 需要额外的恢复密钥/应急流程。

#### 模式三：分阶段（推荐路线）

- **v1 采用模式一**，把数据结构设计成“以后可以升级”的样子（每件内容有独立数据密钥、密钥可重新封装）。
- 后续版本再为**特别敏感的条目**提供可选的端到端模式。
- 优点：先保证可用、可维护、可恢复；不把最复杂的安全问题压在第一版。
- 缺点：v1 仍然不是“管理员也看不到”的绝对保密；宣传时不能夸大。

**推荐：模式三（v1 先做服务器端加密，架构预留升级空间）。** 如果你要求“连管理员也不能看”，需要选模式二，开发周期和复杂度会显著增加。

## 五、经济与时间可行性

## 六、主要风险与应对

| 风险 | 严重程度 | 说明 | 应对措施 |
|---|---|---|---|
| 授权用户泄露解密内容 | 高 | 拍照、另存、转发无法彻底阻止 | 最小授权、下载开关、屏幕水印、审计、保密制度、及时撤销 |
| 主密钥丢失 | 高 | 服务器端密钥丢失，数据无法解密 | 密钥单独加密备份、离线保存恢复材料、定期演练恢复 |
| 本地硬盘损坏或勒索软件 | 高 | 单机部署的最大现实风险 | 每日备份 + 离线/异机备份；定期验证备份可恢复；系统更新和杀毒 |
| 服务器管理员不可信 | 中高 | 服务器端加密下，最高权限者可取钥匙 | 选择模式二（端到端）或严格限制管理员；后续支持可选端到端 |
| 账号被撞库/弱密码 | 高 | 登录口令是常见突破口 | Argon2id、密码强度要求、登录限速、失败锁定、后续双因素认证 |
| 网络被窃听 | 中 | 局域网也可能被抓包 | 全程 HTTPS；远程访问用 VPN；禁止明文 HTTP |
| 权限配置错误 | 中 | 误把内容授权给错误的组 | 授权预览、二次确认、变更审计、定期权限复核 |
| 误删数据 | 中 | 管理员误操作 | 回收站、二次确认、永久删除需再次验证、备份 |
| 软件漏洞 | 中 | 任何软件都可能有漏洞 | 依赖扫描、安全头、最小权限、及时升级、代码审查 |
| 应用端分发风险 | 中低 | 安装包被篡改、SmartScreen 警告 | 校验值、代码签名（可选）、只从可信来源下载 |
| 合规风险 | 中 | 涉及个人信息、密码法规、开源许可证 | 商用/公开服务前咨询法律专业人士；许可证单独确认 |
| 元数据泄露 | 中 | 标题、文件名等可能暴露信息 | 敏感内容应用层加密；原始文件名加密；开启 BitLocker；限制日志 |

## 七、可行性结论

1. **技术可行**：加密、权限、文件存储、网页/客户端、审计、备份都有成熟方案，没有绕不过去的技术障碍。
2. **最大的难点不是写代码，而是先把三件事定清楚**：
   - 应用端到底是电脑软件还是手机 App；
   - 使用范围是单机、局域网还是互联网；
   - 加密信任模式选“服务器保管钥匙”还是“用户自己保管钥匙”。
3. **本方案能可靠满足**“管理员加密上传、按组/按人授权、只有授权用户能查看解密、文件无法直接打开、操作可追溯”的核心目标。
4. **本方案不能承诺**“防止授权用户外泄”“防住恶意服务器最高管理员”“绝对不丢数据”；这些需要靠制度、备份、端到端加密等额外措施。
5. **建议第一版范围**：本地部署、局域网使用、网页端 + 桌面客户端、服务器端加密、小团队、审计 + 备份。先做扎实，再扩展云端、手机原生和端到端加密。
6. **开发前必须确认**下面 5 件事；确认后我会先写第 1 阶段的 spec，经你审阅同意后才开始写代码。

## 九、需要你拍板的 5 件事

> 你只需要看每个问题的“像什么 / 优点 / 缺点 / 推荐”，然后回复选项。没有选定前，我不会开始写代码。

### D1. “应用端”具体指什么？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 电脑桌面软件 + 网页端** | 给电脑装一个“保险箱客户端”，浏览器也能用 | 与网页共用界面，开发快；适合办公室电脑；权限和网页一致 | 手机上只能用浏览器；桌面安装包需要更新 |
| **B. 手机 App + 网页端** | 手机装一个 App，电脑用浏览器 | 手机使用方便；可推送/生物识别 | 要分别做 Android/iOS、上架商店、适配屏幕；成本最高 |
| **C. 电脑 + 手机都要** | 两个客户端都做，分两期 | 覆盖最全 | 第一版周期最长；建议先做电脑端，手机端第二期 |

**推荐：A（电脑桌面软件 + 网页端）。** 如果你的真实场景是手机为主，请选 B，我会重新调整方案和阶段。

### D2. 使用范围是哪里？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 只在你这台电脑上使用** | 保险箱只开在你自己家里 | 最简单、最安全，不需要网络配置 | 其他人无法访问，不满足多人授权查看的需求 |
| **B. 同一局域网/办公室内多人使用** | 保险箱放在办公室，同事在同一个网络里凭门禁进入 | 满足多人协作；不暴露到公网；成本低 | 需要一台常开的主机；离开办公室网络就无法访问 |
| **C. 互联网远程访问（任何地方）** | 保险箱放在云上，随时随地访问 | 最方便 | 需要公网 IP/域名/证书/VPN，安全风险和运维成本最高 |

**推荐：B（局域网多人使用），架构上为以后升级到 C 留余地。** 如果你现在就要求随时随地访问，请选 C，我会把 HTTPS、域名、防火墙和远程安全单独列为一个阶段。

### D3. 谁掌握“钥匙”？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 服务器保管钥匙（服务器端加密）** | 银行保管保险箱钥匙，验证身份后帮你开 | 简单、可恢复、权限撤销快；防硬盘/备份被偷 | 服务器最高管理员理论上能解密；不能宣传“管理员也看不到” |
| **B. 用户自己保管钥匙（端到端加密）** | 每人自己带钥匙，银行也打不开 | 服务器被攻破也拿不到明文；对管理员保密 | 忘记密码/丢钥匙可能永久丢数据；授权和撤销复杂；开发成本高 |
| **C. 先 A 后 B（分阶段）** | 先用银行钥匙，以后给最敏感的柜子换用户自己的锁 | v1 简单可用；架构预留升级；未来可加强 | v1 仍不是端到端；升级需要额外开发和迁移 |

**推荐：C（第一版服务器端加密，预留端到端升级空间）。** 如果你要求“连服务器管理员也不能看”，选 B；但请同时接受密钥丢失导致数据永久无法恢复的风险。

### D4. 整体技术路线选哪条？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. Python 后端 + React 网页 + 桌面客户端外壳** | 后厨用 Python，前厅用网页，客户端装个外壳 | 安全逻辑清楚、开发快、易维护、开源友好 | 两套语言；桌面外壳和服务器部署稍多步骤 |
| **B. 全 TypeScript（网页 + 后端 + Electron）** | 前后厨都用同一种语言和工具 | 前后端统一；桌面端整合自然 | 依赖多、安装包大；安全配置要求高 |
| **C. 基于现成开源项目二次开发** | 买精装房改格局 | 上线快，有现成功能 | 难完全贴合需求；受上游架构和许可证限制；不适合做长期自有产品 |

**推荐：A。** 如果你更看重“只学/只维护一种语言”，可选 B；但不建议选 C 作为长期主线。

### D5. 授权用户能不能把文件下载走？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 授权即可下载，所有下载留痕** | 有门禁的人可以把东西带出去，但门口有记录 | 简单直接，符合“查看并解密”的原始需求；文件可用性最好 | 下载后无法再保护；可能被转发 |
| **B. 每条内容单独设置“可查看/可下载”** | 有些柜子只能看，有些可以带走 | 权限更细，能降低泄露面 | 配置更复杂；文件“只看不下载”需要在线预览，开发成本更高 |
| **C. 一律不允许下载，只在线查看** | 只能在保险箱里看，不能带走 | 最安全 | 很多文件类型无法在线预览；使用不便；开发成本最高 |

**推荐：A（第一版授权即可下载 + 全程留痕），并在界面和文档中明确提示风险。** 后续版本可以增加 B 的细分权限和在线预览。如果文件极其敏感、坚决不能落地，请选 C 或 B，我会相应调整阶段计划。

## 附录：名词小抄

| 名词 | 用大白话解释 |
|---|---|
| 加密 | 把内容变成只有钥匙才能还原的乱码 |
| 解密 | 用钥匙把乱码还原成原内容 |
| 密钥/钥匙 | 一串很长的密码，用来加密和解密 |
| AES-256-GCM | 一种国际通用的加密方法，既保密又能发现篡改 |
| 哈希 | 单向“指纹”，只能用来核对密码，不能还原密码 |
| Argon2id | 一种故意算得很慢的密码保护方法，让暴力破解更困难 |
| HTTPS/TLS | 浏览器和服务器之间的加密传输通道 |
| RBAC | 按角色分配权限，例如管理员/普通用户 |
| 用户组 | 把若干用户放在一起，按组授权，省得一个个设置 |
| 服务器端加密 | 服务器拿到数据后加密，钥匙由服务器保管 |
| 端到端加密 | 数据在用户设备上就加密，服务器只存密文，也打不开 |
| 本地部署 | 软件和数据放在你自己的电脑/服务器上，不放到云上 |
| 备份 | 另外保存一份，主数据坏了可以恢复 |
| 审计日志 | 记录谁在什么时候做了什么，便于追查 |
| PWA | 用网页技术做的“可安装到手机/电脑桌面的网页应用” |
| Spec（规格说明） | 每个阶段开工前写清楚“做什么、怎么做、怎么验收”的文档 |
