## 一、本阶段目标

把“账号系统”做成后续所有功能的地基：

1. 确定用户数据结构，支持管理员和普通用户两种角色。
2. 第一次启动时，安全地创建第一个管理员。
3. 用户可以登录、退出、查看自己的信息、修改密码。
4. 管理员可以创建用户、停用/启用用户、重置密码、解锁账号、调整角色。
5. 登录会话有超时和失效机制，停用/改密后旧会话立即失效。
6. 连续输错密码会临时锁定；管理员可以解锁。
7. 提供最小可用的登录页、首次设置页、改密页和用户管理页。
8. 后端接口、前端页面、安全规则都有自动化测试。
9. 不引入文件、用户组、内容授权等下一阶段功能。

## 三、需要你拍板的关键决定

### 3.1 D2-1：用户表怎么建？

目前 Django 使用的是内置用户表 `auth_user`。它够用，但字段是“通用模板”，后续要加显示名、角色、锁定状态、强制改密标记时，会比较别扭。

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 自定义用户表（推荐）** | 按我们的需求定做一张身份证模板 | 字段干净；角色、显示名、锁定、强制改密都能自然表达；长期扩展最方便；现在数据库里没有用户，是切换的最佳时机 | 需要备份并重建当前**空的**开发数据库；旧库保留可回退 |
| **B. 默认用户表 + 附加资料表** | 用通用身份证，再挂一个资料袋 | 不用重建数据库；也能保存角色等额外信息 | 每次查用户要多关联一张表；代码更绕；以后改登录方式或字段更麻烦 |
| **C. 只用默认用户表** | 只借通用身份证，资料硬塞在现有字段里 | 最简单，不用重建 | 角色/显示名/锁定状态没有合适位置，容易混乱；不推荐长期使用 |

**推荐：A（自定义用户表）。**

原因：

- 现在是切换成本最低的时刻：数据库里 0 个用户，没有任何真实账号或文件。
- 自定义表能直接包含“角色、显示名、是否必须改密、失败次数、锁定时间”等字段，后续阶段不用反复打补丁。
- 旧数据库不会直接删除：会先做完整性检查、复制到 `data/backups/`，再重建新库；万一失败可以回退。

> **需要你明确同意**：如果选择 A，我会先停止服务、备份旧数据库，再替换 `data/db/db.sqlite3` 并重新迁移。当前数据库没有用户数据，所以不会丢失个人资料或文件；旧库保留在备份目录。**你同意后我才会执行；不会先斩后奏。**

### 3.2 D2-2：登录方式

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 服务器会话 + Cookie + CSRF（推荐）** | 进门发一张门禁卡，服务器记得卡号，可以随时挂失 | Django 自带、成熟；会话可立即作废；HttpOnly Cookie 不暴露给页面脚本；跨站请求伪造有现成防护 | 需要浏览器正确携带 Cookie；未来如果做完全独立的原生客户端，可能要补一套令牌机制 |
| **B. JWT 令牌** | 一张自带签名的纸票，服务器不记名单 | 前后端更“分离”；适合多个独立客户端 | 退出/封禁/改密后立即作废比较麻烦；令牌存哪里容易出错；本项目暂时不需要 |
| **C. 混合：网页用会话，桌面端用令牌** | 网页发门禁卡，桌面端发纸票 | 覆盖两种客户端 | 两套认证逻辑，开发和测试成本明显增加；可以等桌面端真正需要时再加 |

**推荐：A（服务器会话 + Cookie + CSRF）。**

原因：本阶段只有网页端；桌面客户端在第 6 阶段如果直接加载同一套网页界面，会话机制可以复用。服务器会话还有一个关键好处：**停用账号或重置密码后，可以立即让旧会话失效**，这比 JWT 简单可靠。

### 3.3 D2-3：第一个管理员怎么创建？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 网页首次设置向导（推荐）** | 第一次入住时，在门口设置管理员账号和密码 | 对非技术用户最友好；不需要命令行；首次设置完成后入口自动关闭 | 需要在后端增加一个“仅本机、仅首次”的初始化接口；必须防止被远程抢先设置 |
| **B. 命令行/脚本创建** | 用服务器钥匙在后台开一个管理员账号 | 攻击面最小；不依赖网页接口 | 对不懂命令行的人不友好；每次初始化要开终端 |
| **C. 预设默认管理员** | 出厂就带一个默认账号和密码 | 最省事 | 默认密码极容易被猜到；严重不安全；不推荐 |

**推荐：A（网页首次设置向导）。**

安全限制：

- 只有在**系统里一个用户都没有**时，初始化接口才可用。
- 只接受来自**本机**（`127.0.0.1` / `::1`）的请求；远程用户即使知道地址也无法完成初始化。
- 首次管理员创建成功后，接口立即关闭；不能再次创建“第二个首个管理员”。
- 创建过程要求 CSRF 令牌，失败不会留下半个管理员。
- 首次设置完成后，前端跳转到登录页，不自动登录，避免会话和 CSRF 切换的混乱。
- 后续把系统开放到局域网前，必须先在本机完成初始化。

### 3.4 D2-4：安全强度选哪档？

| 选项 | 像什么 | 密码要求 | 登录失败锁定 | 会话空闲/最长 | 适合 |
|---|---|---|---|---|---|
| **A. 平衡（推荐）** | 门锁够结实，日常不折腾 | 至少 12 位，允许长密码/空格，不强制大小写符号组合 | 连续失败 5 次，锁 15 分钟 | 空闲 30 分钟 / 最长 8 小时 | 小团队、内部系统 |
| **B. 严格** | 银行金库级门禁，进出更麻烦 | 至少 16 位，同样的弱密码拦截 | 连续失败 3 次，锁 30 分钟 | 空闲 15 分钟 / 最长 4 小时 | 高风险、少数人使用 |
| **C. 宽松** | 家里门锁，方便优先 | 至少 8 位 | 连续失败 10 次，锁 10 分钟 | 空闲 2 小时 / 最长 24 小时 | 不推荐作为默认 |

**推荐：A（平衡）。**

同时会固定采用以下安全措施，不随选项变化：

- 密码使用 **Argon2id** 哈希保存，数据库和日志中没有明文密码。
- 拦截常见弱密码、纯数字密码、与用户名过于相似的密码。
- 用户名统一转小写，3–32 位，只允许字母、数字、下划线和连字符；显示名可使用中文。
- 登录失败提示不区分“用户不存在”和“密码错误”，减少账号探测。
- 登录接口有频率限制；账号达到失败阈值后锁定。
- 管理员不能停用自己、不能降低自己的角色、不能通过管理员接口重置自己的密码；请另一名管理员操作，或使用“修改密码”。
- 最后一名启用中的管理员不能被停用或降级。
- 停用账号、重置密码、修改密码后，旧会话立即失效（改密时保留当前会话）。
- 所有账号管理动作写安全日志；第 7 阶段再做可查询的审计界面。

### 3.5 本阶段实现默认值（不阻塞确认）

- 前端路由使用 **React Router**；本阶段不引入 UI 组件库，沿用第 1 阶段的简洁样式，第 5 阶段再统一设计。
- 前端不把登录令牌放进 `localStorage`；只依赖 HttpOnly 会话 Cookie，页面刷新后重新查询当前用户。
- 用户没有邮箱、手机号、头像、自助注册；账号由管理员创建。
- 不提供“删除用户”，只提供停用/启用，保留审计和历史关联。
- 不使用邮件找回密码；忘记密码由管理员重置。
- 不提供双因素认证，留到后续版本。

## 四、角色与权限

### 4.1 角色

| 角色 | 通俗解释 | 本阶段能做什么 |
|---|---|---|
| 管理员 | 系统管理员 | 管理用户账号和角色；停用/启用；重置密码；解锁；查看用户列表；修改自己的密码 |
| 普通用户 | 被邀请使用系统的人 | 登录、退出、查看自己的信息、修改自己的密码 |

> 管理员的“内容查看/解密权”不在此阶段自动获得；未来内容条目按第 3、4 阶段规则单独授权。

### 4.2 账号状态

| 状态 | 含义 | 能否登录 |
|---|---|---|
| 启用 | 正常账号 | 可以（满足密码/锁定条件时） |
| 停用 | 管理员主动停用 | 不可以；已登录会话立即失效 |
| 锁定 | 连续输错密码触发 | 暂时不可以；到期自动解除，或管理员解锁 |
| 必须改密 | 管理员创建/重置后的临时状态 | 可以登录，但在改密前只能访问“我的信息、修改密码、退出” |

### 4.3 权限矩阵

| 操作 | 管理员 | 普通用户 |
|---|---|---|
| 首次设置（仅无用户时、仅本机） | 可以 | 可以（第一次部署时） |
| 登录、退出 | 可以 | 可以 |
| 查看自己的信息 | 可以 | 可以 |
| 修改自己的密码 | 可以 | 可以 |
| 查看用户列表 | 可以 | 不可以 |
| 创建用户 | 可以 | 不可以 |
| 修改用户显示名 | 可以 | 不可以 |
| 停用/启用用户 | 可以（不能停用自己） | 不可以 |
| 重置用户密码 | 可以（不能重置自己） | 不可以 |
| 解锁用户 | 可以 | 不可以 |
| 调整用户角色 | 可以（不能改自己的角色） | 不可以 |
| 删除用户 | 不可以（用停用代替） | 不可以 |
| 停用/降级最后一名管理员 | 不可以 | 不适用 |

### 4.4 管理员保护规则

- 系统至少保留一名**启用状态**的管理员。
- 不能停用、降级或删除最后一名启用中的管理员。
- 管理员不能停用自己，也不能降低自己的角色；必须由另一名管理员操作。
- 管理员不能通过“管理员重置密码”接口重置自己的密码；请使用“修改密码”。
- 管理员人数不设硬性上限；界面会提示建议保持 1–2 名，以减少账号被攻破后的影响面。

## 五、账号数据设计

### 5.1 用户字段（通俗版）

| 字段 | 用途 | 规则 |
|---|---|---|
| 用户名 | 登录名 | 3–32 位，小写字母/数字/下划线/连字符；唯一；创建后不可改 |
| 显示名 | 界面上显示的名字 | 1–50 字，可用中文；管理员可改 |
| 密码哈希 | 验证密码 | 使用 Argon2id；绝不保存明文；接口永远不返回 |
| 角色 | 管理员/普通用户 | 默认普通用户；创建管理员或调整角色需管理员操作 |
| 是否启用 | 停用/启用 | 停用后不能登录，旧会话失效 |
| 是否必须改密 | 首次登录/重置后强制改密 | 管理员创建或重置的用户为“是”；改密后清除 |
| 失败次数 | 连续输错密码的计数 | 登录成功清零；达到阈值锁定 |
| 锁定截止时间 | 临时锁定到什么时候 | 到期自动解除；管理员可提前解锁 |
| 最后登录时间 | 展示和排查 | 由登录行为更新 |
| 创建人/创建时间/更新时间 | 追溯 | 系统自动记录 |

### 5.2 密码与登录标识

- 登录只使用用户名 + 密码；本阶段不使用邮箱/手机号。
- 密码长度 12–128（按“平衡”档）；允许空格和长密码短语。
- 密码不能与用户名/显示名过于相似，不能是常见弱密码，不能是纯数字。
- 用户名字母统一转小写后再保存和比较，避免 `Admin` 与 `admin` 被当成两个账号。
- 密码重置后生成/输入临时密码，用户下次登录必须修改。
- 不向普通用户暴露“账号是否被锁定”的详细信息；登录失败统一提示，锁定提示只说明“尝试次数过多，请稍后再试”。

### 5.3 会话与登录记录

- 使用数据库存储会话，便于服务端强制失效。
- 会话 Cookie 设置 HttpOnly、SameSite=Lax；HTTPS 启用后再加 Secure。
- 空闲超时和最长有效期按 D2-4 选择执行。
- 停用账号、管理员重置密码、用户修改密码时，清理该用户的其他会话。
- 登录成功/失败、锁定、解锁、创建/停用/启用/改角色、重置密码都写安全日志；第 7 阶段再提供审计查询界面。

## 六、核心流程

### 6.1 首次设置

1. 启动系统，数据库里没有任何用户。
2. 前端调用“设置状态”接口，得知需要初始化。
3. 显示首次设置页：用户名、显示名、密码、确认密码。
4. 前端先取得 CSRF 令牌，再提交设置请求。
5. 后端依次检查：
   - 当前仍然没有任何用户；
   - 请求来自本机；
   - 用户名、密码符合规则；
   - 两次密码一致。
6. 在一个数据库事务中创建管理员；如果失败，不留下部分数据。
7. 设置入口自动关闭；前端跳转到登录页，提示“管理员创建成功，请登录”。

**边界**：如果已经有一个用户，哪怕已被停用，首次设置也不会重新开放；忘记密码走管理员重置或服务器命令行恢复。

### 6.2 登录

1. 用户在前端输入用户名和密码。
2. 后端检查账号是否存在、是否启用、是否锁定。
3. 验证密码：
   - 成功：清零失败次数，建立新会话，记录登录时间，返回用户信息。
   - 失败：失败次数加一；达到阈值后锁定；返回统一的“用户名或密码错误”。
4. 如果用户处于“必须改密”状态，前端跳转到修改密码页；在改密前，其他业务接口全部拒绝访问。
5. 登录失败达到阈值后，锁定到期自动解除；管理员也可以在用户管理页提前解锁。
6. 登录接口额外做 IP 级限速，默认同一 IP 每分钟最多 20 次尝试；这是账号锁定的补充，不替代账号锁定。

### 6.3 退出登录

1. 用户在页面点击“退出”。
2. 前端调用退出接口。
3. 后端销毁当前会话。
4. 前端清理页面内的用户状态，回到登录页。
5. 不使用浏览器本地存储保存敏感信息。

### 6.4 修改自己的密码

1. 已登录用户输入当前密码、新密码、确认新密码。
2. 后端验证当前密码、新密码规则、两次输入一致。
3. 更新密码哈希，清除“必须改密”标记。
4. 保留当前会话，清理该用户的其他会话。
5. 记录安全日志；不记录任何密码内容。

### 6.5 管理员创建用户

1. 管理员进入“用户管理”，点击“新建用户”。
2. 填写用户名、显示名、初始密码、角色。
3. 后端检查权限、用户名唯一性、密码规则、角色合法性。
4. 创建用户，标记“必须改密”。
5. 管理员把用户名和临时密码通过可信方式告诉用户；系统不在日志或接口响应中回传密码。
6. 用户首次登录后必须修改密码。

### 6.6 停用/启用用户

- 管理员可以停用普通用户；停用后：
  - 立即删除该用户所有会话；
  - 该用户无法登录；
  - 历史记录保留；不物理删除账号。
- 管理员可以重新启用用户；启用后用户可重新登录。
- 管理员不能停用自己；最后一名启用管理员不能被停用。
- 管理员人数不设硬性上限；启用管理员账号不需要额外的人数检查，但仍受“至少保留一名启用管理员”的规则约束。

### 6.7 重置密码与解锁

- 管理员为其他用户设置临时密码：
  - 临时密码必须符合密码规则；
  - 用户被标记为“必须改密”；
  - 该用户所有旧会话立即失效；
  - 记录操作者、目标和时间。
- 管理员可以解锁被临时锁定的用户；解锁后失败次数清零。
- 管理员不能通过此接口重置自己的密码。

### 6.8 调整角色

- 只有管理员可以调整别人的角色。
- 管理员不能调整自己的角色。
- 把最后一名启用管理员降级会被拒绝。
- 角色修改后记录安全日志；不自动销毁该用户的会话（角色权限在下一次请求时按新角色判断），但如果被降级，下一次访问管理员接口会被拒绝。

### 6.9 会话超时与失效

- 空闲超时：超过设定时间没有操作，要求重新登录。
- 最长有效期：从登录开始算，超过后必须重新登录。
- 停用账号、重置密码：立即失效该用户全部会话。
- 修改自己的密码：保留当前会话，其他会话失效。
- 前端收到未登录/无权限响应时，清理页面状态并回到登录页。

### 6.10 忘记密码/应急恢复

- 普通用户：请管理员重置临时密码。
- 管理员忘记密码：
  - 如果还有另一名管理员，可由对方重置；
  - 如果只有一名管理员，可在**运行服务的电脑上**使用 Django 自带的 `changepassword` 命令重置；
  - 锁定会在到期后自动解除；也可以在服务器命令行中清除锁定状态（需要服务器访问权限）。
- 这些操作需要物理/服务器访问权限，不通过网页开放，避免成为新的攻击面。
- 应急命令会写入 README 和运维说明；本阶段不提供网页“忘记密码”功能。

## 七、API 设计（初稿）

所有接口使用 `/api/v1/` 前缀，JSON 格式。除特别说明外，状态变更请求必须带 CSRF 令牌。

### 7.1 初始化与认证

| 方法 | 路径 | 谁能调用 | 说明 |
|---|---|---|---|
| GET | `/api/v1/setup/status/` | 任何人 | 返回 `{"needs_setup": true/false}`；只暴露是否还需要初始化 |
| GET | `/api/v1/auth/csrf/` | 任何人 | 设置 CSRF Cookie，返回 204；前端在提交表单前调用 |
| POST | `/api/v1/setup/` | 仅本机 + 无用户 | 创建首个管理员；成功后 201；重复/远程/已有用户返回 409 或 403 |
| POST | `/api/v1/auth/login/` | 任何人 | 用户名+密码；成功返回当前用户；失败 400；锁定 423 |
| POST | `/api/v1/auth/logout/` | 已登录 | 销毁会话，返回 204 |
| GET | `/api/v1/auth/me/` | 已登录 | 返回当前用户信息，不含密码哈希 |
| POST | `/api/v1/auth/change-password/` | 已登录 | 当前密码 + 新密码；成功后保留当前会话、清理其他会话 |

### 7.2 管理员用户管理

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/users/` | 分页列出用户；支持按用户名/显示名搜索；不返回密码哈希 |
| POST | `/api/v1/admin/users/` | 创建用户（用户名、显示名、初始密码、角色） |
| GET | `/api/v1/admin/users/{id}/` | 查看单个用户 |
| PATCH | `/api/v1/admin/users/{id}/` | 修改显示名（用户名不可改） |
| POST | `/api/v1/admin/users/{id}/role/` | 调整角色；不能改自己；保护最后一名管理员 |
| POST | `/api/v1/admin/users/{id}/disable/` | 停用；不能停用自己；立即失效会话 |
| POST | `/api/v1/admin/users/{id}/enable/` | 启用 |
| POST | `/api/v1/admin/users/{id}/reset-password/` | 设置临时密码；不能重置自己；强制改密 + 失效会话 |
| POST | `/api/v1/admin/users/{id}/unlock/` | 清除失败次数和锁定时间 |

### 7.3 响应与错误规则

- 成功返回 JSON 用户信息或分页列表；不返回密码、密码哈希、内部密钥。
- 参数错误：HTTP 400，按字段返回可读错误。
- 未登录/会话过期：HTTP 401 或 403；前端都按“需要重新登录”处理。
- 无权限（普通用户访问管理员接口）：HTTP 403。
- 账号锁定：HTTP 423，提示稍后再试；不暴露更多账号信息。
- CSRF 校验失败：HTTP 403；前端重新获取令牌后可重试。
- 用户不存在/密码错误/账号停用：统一使用“用户名或密码错误”提示，避免探测账号状态。
- 所有写操作记录安全日志；日志中不出现密码、Cookie、CSRF 令牌。

## 八、前端页面

### 8.1 页面清单

| 页面 | 使用者 | 主要内容 |
|---|---|---|
| 首次设置页 | 首次部署者 | 创建管理员；提示“仅本机可完成”；密码规则；成功后去登录 |
| 登录页 | 所有人 | 用户名、密码、错误提示、加载状态 |
| 修改密码页 | 已登录用户 / 必须改密用户 | 当前密码、新密码、确认；强制模式下不显示其他导航 |
| 系统主页 | 已登录用户 | 显示当前用户、角色、欢迎信息；管理员可见“用户管理”入口 |
| 用户管理页 | 管理员 | 用户列表、搜索、新建、停用/启用、重置密码、解锁、调整角色 |
| 未找到/无权限页 | 所有人 | 友好提示和返回入口 |

### 8.2 前端行为

- 打开页面时：
  1. 查询是否需要首次设置；需要则显示设置页。
  2. 不需要则获取 CSRF 令牌，再查询当前登录用户。
  3. 未登录显示登录页；必须改密显示修改密码页；否则显示主页。
- 所有写请求带 CSRF 令牌，并携带 Cookie（`credentials: 'include'`）。
- 会话过期或收到未登录响应：清理页面状态，回到登录页，并提示“登录已过期，请重新登录”。
- 管理员入口只对有管理员角色的用户显示；前端隐藏不等于安全，后端必须再次校验。
- 危险操作（停用、重置密码、调整角色）弹出确认框，说明后果。
- 密码输入框不显示明文；支持密码管理器（正确的 `autocomplete` 属性）。
- 页面中文、响应式，沿用第 1 阶段的简洁视觉风格；本阶段不引入 UI 组件库。
- 路由使用 React Router；刷新页面后仍能定位到正确页面。
- 不把登录令牌/密码写入 `localStorage` 或日志。

## 九、安全要求

| 编号 | 要求 | 说明 |
|---|---|---|
| S2-01 | 密码哈希 | Argon2id；参数使用成熟默认值；不保存明文 |
| S2-02 | 密码策略 | 至少 12 位，拦截常见弱密码、纯数字、与用户名相似 |
| S2-03 | 失败锁定 | 连续 5 次失败锁 15 分钟；成功登录清零；管理员可解锁 |
| S2-04 | 登录限速 | 登录接口有基于 IP 的频率限制（默认 20 次/分钟）；防止短时间大量尝试 |
| S2-05 | 会话安全 | HttpOnly、SameSite=Lax；HTTPS 后加 Secure |
| S2-06 | 会话超时 | 空闲 30 分钟、最长 8 小时（平衡档） |
| S2-07 | 强制改密 | 临时密码用户改密前不能访问其他接口 |
| S2-08 | 会话失效 | 停用/重置密码立即失效；改密保留当前、清理其他会话 |
| S2-09 | CSRF | 所有状态变更请求校验 CSRF；前端正确携带令牌 |
| S2-10 | 跨域 | 仅允许开发前端地址，且允许携带 Cookie；不使用通配符 |
| S2-11 | 初始化保护 | 设置接口仅本机、仅无用户时可用；成功后永久关闭 |
| S2-12 | 最后管理员保护 | 不能停用/降级最后一名启用管理员 |
| S2-13 | 权限校验 | 管理员接口由后端权限类强制检查，不能只靠前端隐藏 |
| S2-14 | 防账号探测 | 登录失败统一提示；不暴露账号是否存在、是否停用 |
| S2-15 | 日志脱敏 | 不记录密码、哈希、Cookie、CSRF 令牌；只记录操作和结果 |
| S2-16 | 输入校验 | 用户名/显示名/角色/密码长度和字符集校验；防注入和越权 |
| S2-17 | 错误处理 | 不向前端返回堆栈、数据库路径、内部配置 |
| S2-18 | 应急恢复 | 仅服务器命令行可重置管理员密码；网页不开放后门 |
| S2-19 | 依赖安全 | Argon2 依赖锁定版本；安装后做一致性检查 |
| S2-20 | 数据库保护 | 数据库继续放在 `data/db/`，不进 Git、不被网页静态提供 |

> 本阶段仍只在本机开发环境使用；局域网/HTTPS 部署的安全要求在第 7 阶段统一加固。

## 十、数据库重建与迁移方案（仅在选择 D2-1 A 时）

### 10.1 当前事实

- 当前数据库中用户数：**0**。
- 仅有 Django 内置表：`auth_*`、`django_session`、`django_content_type`、`django_migrations`。
- 没有文件、密码条目、用户组或任何业务数据。
- 旧数据库会先备份，不会直接删除。

### 10.2 执行步骤

1. 停止后端服务，确保没有连接在写数据库。
2. 对旧数据库执行 `PRAGMA integrity_check`；失败则停止并向你报告。
3. 把 `data/db/db.sqlite3`（以及可能存在的 `-wal`/`-shm` 文件）复制到  
   `data/backups/stage1-before-accounts-YYYYMMDD-HHMMSS/`。
4. 再次确认备份文件可打开、迁移表存在。
5. 把旧数据库重命名/移动到备份目录（**不直接删除**）。
6. 在代码中加入 `accounts` 应用和自定义用户模型，设置 `AUTH_USER_MODEL`。
7. 生成并执行新迁移，创建新数据库。
8. 验证：
   - 新用户表存在；
   - 旧数据库的备份仍在；
   - 首次设置页可用；
   - 0 用户状态下不需要任何迁移错误。
9. 如果任何一步失败：停止开发，恢复旧数据库，向你报告；不继续写入。

### 10.3 回退

- 停止服务；
- 把新数据库移到一边（不删除）；
- 从 `data/backups/stage1-before-accounts-.../` 复制旧数据库回 `data/db/db.sqlite3`；
- 重新启动旧版本并验证。

### 10.4 说明

- 这是**一次性的**开发数据库重建；因为现在没有真实用户，成本最低。
- 从第 2 阶段以后，正常使用 Django 迁移，不再重建数据库。
- 备份目录在 `data/` 下，已被 `.gitignore` 忽略，不会提交到 Git。
- 如果你不选择 D2-1 A，就不执行本节；改用默认用户表 + 资料表方案。

## 十一、验收标准

### 11.1 初始化与登录

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC2-01 | 首次设置状态 | 0 用户时返回需要初始化；创建管理员后返回不需要 |
| AC2-02 | 首次设置 | 本机提交合法信息后创建管理员；密码用 Argon2id；不自动登录 |
| AC2-03 | 设置保护 | 第二个设置请求被拒绝；非本机请求被拒绝；已有用户时被拒绝 |
| AC2-04 | 设置原子性 | 密码不一致/用户名重复/规则不通过时不留下用户 |
| AC2-05 | 登录成功 | 正确用户名密码可登录；会话 Cookie 为 HttpOnly + SameSite=Lax |
| AC2-06 | 登录失败 | 错误用户名/密码/停用账号都返回统一提示，不泄露账号状态 |
| AC2-07 | 失败锁定 | 连续 5 次失败后锁定 15 分钟；锁定期正确密码也不能登录；到期自动解除 |
| AC2-08 | 管理员解锁 | 管理员可提前解锁；解锁后失败次数清零 |
| AC2-09 | 登录限速 | 同一 IP 短时间大量登录请求被限速 |
| AC2-10 | 未登录访问 | 未登录访问业务/管理接口被拒绝；前端回到登录页 |

### 11.2 会话与密码

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC2-11 | 空闲超时 | 超过 30 分钟无操作，下一次请求要求重新登录 |
| AC2-12 | 最长会话 | 登录超过 8 小时后，必须重新登录 |
| AC2-13 | 退出 | 退出后旧会话不能继续访问 |
| AC2-14 | 修改密码 | 需验证当前密码；新密码符合规则；成功后清除强制改密标记 |
| AC2-15 | 改密失效 | 修改密码后，其他会话失效；当前会话保持可用 |
| AC2-16 | 强制改密 | 管理员创建/重置的用户在改密前只能访问“我的信息/改密/退出” |
| AC2-17 | CSRF | 状态变更请求缺少 CSRF 令牌时被拒绝；带正确令牌时成功 |
| AC2-18 | 密码安全 | API 响应、日志、错误页中找不到明文密码或密码哈希 |

### 11.3 用户管理

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC2-19 | 创建用户 | 管理员可创建普通用户；新用户必须改密；普通用户不能调用创建接口 |
| AC2-20 | 停用账号 | 停用后不能登录，旧会话立即失效 |
| AC2-21 | 启用账号 | 重新启用后可登录；停用期间数据保留 |
| AC2-22 | 重置密码 | 管理员重置后旧密码失效、旧会话失效、下次登录强制改密 |
| AC2-23 | 角色调整 | 管理员可调整别人角色；不能调整自己 |
| AC2-24 | 最后管理员保护 | 不能停用/降级最后一名启用管理员；系统始终至少有一名管理员 |
| AC2-25 | 管理员自保护 | 管理员不能停用自己、不能通过管理接口重置自己密码 |
| AC2-26 | 权限隔离 | 普通用户访问用户管理/角色/停用/重置接口均被 403 拒绝 |
| AC2-27 | 用户信息 | 接口不返回密码哈希；用户列表分页、搜索正常 |
| AC2-28 | 操作留痕 | 创建/停用/启用/重置/解锁/改角色/登录失败等都有安全日志，且不含密码 |

### 11.4 数据库与交付

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC2-29 | 数据库备份 | 旧库完整备份存在；校验通过；旧库未被直接删除 |
| AC2-30 | 新库迁移 | 自定义用户表迁移成功；无业务旧数据丢失；0 用户状态可初始化 |
| AC2-31 | 回退演练 | 按文档能恢复旧库并启动；新库可移开保留 |
| AC2-32 | 前端流程 | 首次设置 → 登录 → 强制改密（如适用）→ 主页 → 用户管理 → 退出，完整可用 |
| AC2-33 | 前端权限 | 普通用户界面上看不到用户管理入口，直接访问也由后端拒绝 |
| AC2-34 | 自动化检查 | 后端测试通过、Ruff 通过、前端构建通过、Oxlint 通过 |
| AC2-35 | 响应式 | 手机浏览器宽度下表单和用户列表可用，不横向溢出 |

|---|---|---|
| 重建空数据库 | 误操作导致第 1 阶段状态丢失 | 先完整性检查、备份、保留旧库；失败按回退步骤恢复；当前 0 用户、无业务数据 |
| 自定义用户模型迁移失败 | 无法初始化账号 | 在空库上执行；先测试迁移；失败恢复旧库并报告，不擅自继续 |
| 会话/CSRF 跨端口配置错误 | 登录后立刻掉线/表单 403 | 统一使用 `127.0.0.1`；CORS 白名单 + credentials；自动化测试覆盖 CSRF |
| 账号锁定被滥用 | 恶意者反复输错导致用户暂时无法登录 | 15 分钟自动解除；管理员解锁；后续可加 IP 限速和设备策略 |
| 管理员账号被攻破 | 可重置其他用户/停用账号 | Argon2id、强密码、登录锁定、最后管理员保护、操作日志、建议至少两名管理员 |
| 管理员忘记密码且只有一人 | 无法登录 | 服务器命令行 `changepassword` 应急；README 写明步骤；锁定会自动到期 |
| 初始设置接口被远程抢占 | 攻击者创建首个管理员 | 仅本机、仅 0 用户、成功后关闭；系统本阶段只监听本机 |
| 管理员人数不设上限 | 权限面变大 | 界面提示建议 1–2 名；最后管理员保护；后续可增加更细角色 |
| 强制改密被绕过 | 临时密码用户直接使用系统 | 后端中间件拦截，不只靠前端跳转；测试覆盖 |
| 日志泄露密码 | 凭据泄露 | 日志过滤器 + 不记录请求体 + 测试；安全日志只记录动作 |
| Argon2 在低配电脑上较慢 | 登录变慢 | 使用成熟默认参数；实测登录耗时；必要时调整参数但不降低到不安全水平 |
| 与桌面客户端会话不兼容 | 第 6 阶段返工 | 本阶段选服务器会话；桌面端可加载同一网页；若做独立客户端再单独评估令牌方案 |
| 范围膨胀 | 账号阶段拖长 | 本 spec 明确不做内容/组/审计 UI；新需求进后续阶段 |
