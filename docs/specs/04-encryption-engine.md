## 一、本阶段目标

1. 管理员可以给文字条目填写网址、账号、密码和秘密备注，保存前加密。
2. 管理员可以给文件条目上传文件，文件在写入磁盘前加密；磁盘上没有原始文件名、原后缀或明文。
3. 授权用户可以在网页中查看文字秘密：密码默认打码，点击“显示”才解密；复制密码也留痕。
4. 授权用户可以下载文件；服务器逐个校验权限，下载前验证完整性，全程写安全日志。
5. 未授权用户、停用用户、被撤销授权的人，在内容接口上一律拿不到内容；普通用户未授权时返回 404。
6. 管理员即使能看到条目标题和授权情况，也不会仅因管理员身份自动获得内容解密权。
7. 新增“回收站”：删除进回收站，保留 30 天，可恢复；到期清理。
8. 主密钥与数据库分离；主密钥不以明文落盘，不进数据库、不进日志、不进 Git。
9. 保留第 3 阶段的账号、用户组、条目、授权和页面；使用增量迁移。
10. 为第 5 阶段完整 Web 界面、第 7 阶段加密备份与审计界面打基础。

## 二、前置状态与硬约束

- 第 3 阶段已验收：用户组、成员、条目元数据、组授权、个人授权均可用。
- 真实数据库有 2 个账号；必须保留账号、密码、角色和启用状态。
- 第 3 阶段的占位条目没有真实内容，本阶段迁移后仍然保留；管理员可以按条目类型补充内容。
- 只做增量迁移：新增内容表、给现有条目表增加删除状态字段；不删除旧数据。
- 本阶段仍然只在本机开发环境使用，不开放局域网或公网；HTTPS 在第 7 阶段。
- 所有权限判断在后端完成，前端隐藏按钮不是安全边界。
- 不自行发明加密算法；使用成熟加密库。
- 服务器不落明文临时文件；大文件分块处理，不能一次性读入内存。
- 主密钥、主密码、数据钥匙、明文内容都不进日志、错误提示、前端缓存或 Git。
- 当前是单进程本机服务；多进程/多服务器共享解锁状态不在本阶段范围。

## 三、需要你拍板的关键决定

### 3.1 D4-1：主钥匙怎么保管？

这是本阶段最重要的决定，直接决定“硬盘被偷时数据是否安全”。

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 启动时输入主密码（推荐）** | 保险箱钥匙放在一个需要口令才能打开的盒子里；服务器每次重启，由管理员输入一次主密码解锁 | 主钥匙不以明文落盘；整台电脑或备份被偷，没有主密码也打不开；最符合“防硬盘/备份被偷”的目标 | 每次重启服务都要输入一次；忘记主密码 = 数据永久无法恢复；主密码必须离线妥善保管 |
| **B. 钥匙文件常驻本机** | 钥匙文件放在这台电脑上，服务启动时自动读取 | 重启自动恢复，使用方便；不用每次输入 | 整台电脑被偷时，钥匙和密文一起被拿走，**防不住整盘失窃**；只能防数据库或备份单独泄露 |
| **C. 绑定 Windows 账户** | 用 Windows 账户的“系统钥匙库”保护钥匙 | 不用每次输入；绑定本机账户 | 换电脑、重装系统或 Windows 账户损坏时可能打不开；该 Windows 账户被攻破时同样失效 |

**推荐：A（启动时输入主密码）。**

说明：

- 主密码**不是**你的登录密码。登录密码由每个用户自己使用；主密码只用于解锁服务器上的保险箱。
- 主密码至少 12 位，建议用 4 个不相关的词组成一句长短语。它不会保存在服务器、数据库或 `.env` 中。
- 服务器重启后，内容处于“已锁定”状态。管理员登录后输入主密码即可解锁；普通用户看到“保险箱未解锁，请联系管理员”。
- 主密码可以写在纸上放进保险柜，或放在离线密码管理器中。**不要**把它和数据库备份放在同一块硬盘上。
- 如果你更看重“重启后不用输入”，可以选 B；但请同时接受“整台电脑被偷时加密可能失效”的限制。
- 如果选 A，忘记主密码没有任何找回方式；这不是缺陷，而是加密系统的基本性质。

### 3.2 D4-2：文件怎么加密？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 每条内容一把数据钥匙 + 分块流式加密（推荐）** | 每个档案袋有自己的小钥匙，小钥匙再放进主保险箱；大文件像传送带一样一块一块处理 | 一条内容泄露不影响其他；大文件内存占用低；200 MB 文件也能稳定处理 | 格式和代码更复杂；需要严格测试分块、完整性和中断处理 |
| **B. 每条内容一把数据钥匙 + 整文件一次加密** | 每个档案袋有自己的小钥匙，但必须把整个文件一次搬进内存 | 实现较简单；完整性处理直接 | 200 MB 文件会占用大量内存，低配电脑可能卡顿或失败 |
| **C. 所有内容共用主钥匙直接加密** | 全公司共用一个钥匙，直接锁所有柜子 | 实现最简单 | 一把钥匙泄露，全部内容都危险；无法只更换某一条内容的钥匙 |

**推荐：A（信封加密 + 分块流式 AES-256-GCM）。**

说明：

- “信封加密”就是：每条内容生成一把随机的数据钥匙，用这把钥匙加密内容；再用主钥匙把数据钥匙加密后存进数据库。数据库里只有“被锁住的数据钥匙”，没有明文数据钥匙。
- 文字秘密较小，可以整体放在内存中加密；文件按固定大小分块读取、加密、写盘，内存只保留当前块。
- 使用 AES-256-GCM：它同时提供加密和防篡改。密文被改动、截断或替换，解密会失败，系统拒绝返回内容。
- 每条内容的密文绑定条目标识、类型和加密版本，防止把 A 条目的密文偷换到 B 条目。
- 第 1 版加密版本号固定为 `1`，为以后升级或端到端加密预留。

### 3.3 D4-3：标题和说明要不要加密？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 标题/说明明文，正文加密（推荐）** | 档案盒外面写“财务资料”，盒子里面才是锁起来的文件 | 列表、搜索、审计和管理都简单；与第 3 阶段行为一致；管理员能看到标题 | 标题和说明本身不保密；不能把秘密写进标题/说明 |
| **B. 标题明文，说明加密** | 盒子外面只写名字，里面的说明也锁起来 | 说明可以放稍敏感的信息 | 说明无法搜索；列表和详情要解密说明；管理员也看不到说明 |
| **C. 标题和说明都加密** | 连盒子外面的名字都锁起来 | 管理信息也保密 | 列表无法搜索和排序；每次列表都要解密；性能和管理复杂度明显增加 |

**推荐：A（标题/说明明文，正文加密）。**

说明：

- 第 3 阶段的授权、搜索和管理都依赖标题明文；改成加密会推翻已验收的行为。
- 界面会明确提示：“标题和说明不加密，请不要把密码、密钥或敏感细节写在标题/说明里。”
- 原始文件名会加密保存，不会出现在磁盘文件名中；但条目标题仍是明文。

### 3.4 D4-4：文字秘密包含哪些字段？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 固定字段：网址、账号、密码、秘密备注（推荐）** | 一张固定格式的密码卡片 | 页面统一；密码可以单独打码和复制；最容易做对权限和审计 | 不能随意增加字段；分类/标签放到第 5 阶段 |
| **B. 一整段自由文本** | 一张空白纸，想写什么写什么 | 最灵活；实现最简单 | 无法单独打码密码；无法结构化复制；容易漏字段 |
| **C. 自定义字段** | 自己设计每张卡片的栏目 | 最灵活 | 第一版复杂度过高；界面和校验难统一 |

**推荐：A（固定字段：网址、账号、密码、秘密备注）。**

说明：

- 这四个字段作为整体加密保存；标题、类型、说明仍属于公开管理信息。
- 密码默认打码，点击“显示”才解密；账号和网址在打开条目时显示。
- 分类、标签、密码生成器、密码历史放到后续阶段，不阻塞本阶段。
- “秘密备注”与条目的公开“说明”不同：秘密备注在加密内容里，说明是明文管理信息。

### 3.5 D4-5：删除内容时怎么处理？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 删除进回收站，保留 30 天（推荐）** | 像电脑回收站，误删还能捡回来 | 防误删；30 天内可恢复；到期自动清理 | 多一层状态和清理逻辑；删除后 30 天内密文仍占空间 |
| **B. 只归档，不提供删除** | 把文件放到“已下架”柜子，永远不扔 | 最简单；不会误删 | 无法真正清掉不要的内容；用户想删除时没有出口 |
| **C. 立即永久删除** | 直接碎纸机 | 最彻底 | 误删无法恢复；不符合数据安全原则 |

**推荐：A（30 天回收站）。**

说明：

- “归档”和“删除”不同：归档是暂时从普通用户列表下架，管理员仍可在归档列表看到；删除是进回收站，普通用户和管理员默认列表都看不到，只能到回收站恢复。
- 回收站保留 30 天；到期由系统清理密文和数据库记录，并写安全日志。
- 本阶段先做“删除、恢复、到期自动清理”；手动“立即永久删除”的按钮和再次验证身份放到第 5 阶段，避免误操作。
- 删除不会立刻删除密文文件；恢复后内容仍可解密，前提是主密码正确、文件未损坏。

### 3.6 D4-6：使用哪个加密库？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. `cryptography`（PyCA，推荐）** | 一家被大量软件使用的正规锁厂 | 成熟、维护活跃；支持 AES-256-GCM 和流式加解密；Python 生态常用 | 增加一个第三方依赖；需要锁定版本并关注安全更新 |
| **B. `pycryptodome`** | 另一家老牌锁厂 | 成熟；API 直接；也支持 AES-GCM | 与 `cryptography` 生态不同；需要另做依赖和漏洞管理 |
| **C. 自己写加密代码** | 自己画图纸造锁 | 看起来自由 | 极不安全；一个细节错误就可能让加密形同虚设；不推荐 |

**推荐：A（`cryptography`）。**

说明：

- 我们只使用它提供的标准算法接口，不自创加密算法或填充方式。
- 依赖版本会写进 `requirements.txt` 并锁定；开源前做依赖漏洞扫描。
- 主密码派生使用项目已有的 Argon2id（`argon2-cffi`），不额外引入新的口令哈希库。

## 四、角色与权限矩阵

| 操作 | 管理员 | 普通用户 |
|---|---|---|
| 添加/编辑文字内容 | 可以（任意管理员） | 不可以 |
| 上传/替换文件内容 | 可以（任意管理员） | 不可以 |
| 查看条目标题/说明/授权 | 可以（全部） | 只能看被授权的 |
| 查看文字秘密（网址/账号/备注） | 仅所有者或被授权时 | 仅被授权时 |
| 显示密码 | 仅所有者或被授权时 | 仅被授权时 |
| 复制密码并留痕 | 仅所有者或被授权时 | 仅被授权时 |
| 下载文件 | 仅所有者或被授权时 | 仅被授权时 |
| 归档/恢复 | 可以 | 不可以 |
| 删除到回收站/恢复 | 可以 | 不可以 |
| 到期清理回收站 | 系统执行 | 系统执行 |
| 初始化主密码 | 第一位操作的管理员 | 不可以 |
| 解锁/锁定保险箱 | 知道主密码的管理员 | 不可以 |
| 管理组/授权 | 沿用第 3 阶段 | 不可以 |

**边界**：

- 管理员可以看到“这条内容存在、标题是什么、谁有权限”，但不能仅凭管理员身份解密。
- 如果管理员需要查看某条内容，必须像普通用户一样被授予个人或组权限；显式给自己授权会写日志。
- 解锁主密码只解决“服务器能否解密”；具体某条内容还要再通过所有者/授权检查，二者缺一不可。

## 五、数据设计

### 5.1 新增内容表

新增 `VaultContent`，与 `VaultItem` 一对一：

| 字段 | 用途 | 说明 |
|---|---|---|
| `item` | 对应条目 | 一对一；一个条目最多一份当前内容 |
| `content_type` | `text` / `file` | 必须与条目类型一致 |
| `encryption_version` | 加密格式版本 | 第 1 版固定 `1` |
| `key_version` | 主钥匙版本 | 第 1 版固定 `1`，为以后换钥匙预留 |
| `wrapped_dek` | 被主钥匙加密的数据钥匙 | 二进制；数据库里没有明文数据钥匙 |
| `dek_nonce` | 包裹数据钥匙用的随机数 | 二进制 |
| `payload_nonce` | 文字内容加密随机数 | 文件内容放在密文文件头里 |
| `encrypted_payload` | 文字密文 | 仅文字条目；数据库中的乱码 |
| `blob_path` | 文件密文的相对路径 | 随机、无意义的文件名；仅文件条目 |
| `ciphertext_size` | 密文大小 | 用于磁盘与下载校验 |
| `plaintext_size` | 原始大小 | 用于显示和下载长度 |
| `plaintext_sha256` | 原始内容校验值 | 解密后再校验一次 |
| `encrypted_metadata` | 加密的文件名/类型等 | 只有授权者解密后可见 |
| `metadata_nonce` | 加密元数据的随机数 | 二进制 |
| `created_by` / `created_at` / `updated_at` | 创建与更新时间 | 内容变更留痕 |

### 5.2 现有条目表的新增字段

`VaultItem` 增加：

| 字段 | 用途 |
|---|---|
| `is_deleted` | 是否在回收站 |
| `deleted_at` | 删除时间，用于 30 天计算 |
| `deleted_by` | 执行删除的管理员 |

- 默认 `is_deleted=False`；现有条目迁移后都是未删除状态。
- 归档状态 `is_archived` 继续保留。
- 普通用户的可见条件：未归档、未删除、并且有有效授权。

### 5.3 主密钥材料

主密钥文件位置：

```text
data/keys/master.key.json
```

文件内容只包含：

- 版本号；
- Argon2id 随机盐和参数；
- 被主密码派生钥匙加密后的主密钥；
- 加密随机数；
- 创建时间；
- 不包含主密码、不包含明文主密钥。

主密钥本身：

- 随机生成 256 位；
- 只在解锁后存在服务器内存；
- 不写数据库、不写日志、不进 Git、不通过网页静态目录暴露；
- 服务器重启后自动消失，需要重新输入主密码。

### 5.4 文件密文格式

磁盘上的文件密文放在：

```text
data/vault/objects/<随机编号>.vault
```

- 文件名与原始文件名无关，没有原后缀。
- 文件头包含格式标识、版本、随机数；后面是密文和认证标签。
- 加密时边读边写，内存只保留当前分块。
- 下载前先完整验证认证标签，再开始向浏览器发送数据；验证失败返回“内容损坏或被篡改”，不发送明文。
- 原始文件名、MIME 类型加密保存在 `encrypted_metadata`，只发给有权查看内容的人。

### 5.5 文字内容格式

- 四个字段组成 JSON：`url`、`username`、`password`、`notes`。
- 整个 JSON 用该条目的数据钥匙加密，存进 `encrypted_payload`。
- 密码为空是允许的；查看接口默认不返回密码，只返回“是否设置了密码”。
- 显示密码和复制密码分别写安全日志。

### 5.6 密钥层级

```text
管理员的主密码
  → Argon2id 派生出“开锁钥匙”
  → 解开主密钥（只在内存）
  → 主密钥解开每条内容的数据钥匙
  → 数据钥匙解开文字或文件内容
```

- 换主密码时只需要重新包裹主密钥，不需要重新加密所有内容；本阶段不做换主密码，后续再做。
- 每条内容的数据钥匙独立；替换内容时生成新的数据钥匙。

### 5.7 迁移与旧数据

- 只新增 `VaultContent` 表和 `VaultItem` 的三个删除状态字段。
- 现有条目没有内容记录，显示为“尚未添加内容”；管理员可以补充。
- 不自动生成主密钥；第一次添加内容时由管理员设置主密码。
- 迁移前备份，迁移后核对账号和旧条目数量；失败可按备份回退。

## 六、核心流程

### 6.1 第一次设置主密码

1. 管理员打开一个没有内容的条目，点击“添加加密内容”。
2. 系统发现还没有主密钥，显示“第一次使用加密功能”。
3. 管理员设置主密码（至少 12 位）并确认。
4. 系统生成主密钥，用主密码派生钥匙包裹后写入 `data/keys/master.key.json`。
5. 系统提示：主密码不会保存在服务器；丢失将无法恢复；请立即离线保存。
6. 管理员确认后，主密钥进入内存，内容添加流程继续。

### 6.2 服务器重启后解锁

1. 管理员登录，打开内容页面。
2. 系统显示“保险箱已锁定”。
3. 管理员输入主密码。
4. 正确：主密钥进入内存，内容可查看/下载；错误：统一提示“主密码不正确”，并限速/记录日志。
5. 普通用户看到“保险箱未解锁，请联系管理员”，不能自行解锁。

### 6.3 添加文字秘密

1. 管理员打开文字类型条目，点击“添加内容”。
2. 填写网址、账号、密码、秘密备注。
3. 系统检查主钥匙已解锁、条目类型匹配、权限为管理员。
4. 系统生成数据钥匙，加密四个字段，保存内容记录。
5. 界面显示“已加密保存”；日志记录内容创建，不记录字段值。

### 6.4 编辑文字秘密

1. 管理员打开已有文字内容，点击“编辑”。
2. 可修改网址、账号、秘密备注；密码留空表示不修改，另有“清空密码”选项。
3. 保存时生成新的数据钥匙和新的随机数，重新加密整份内容。
4. 旧密文被覆盖；写内容更新日志。
5. 如果保存失败，旧内容保持可用，不能出现“改到一半”的状态。

### 6.5 上传文件

1. 管理员打开文件类型条目，点击“上传文件”或“替换文件”。
2. 选择文件；系统检查大小上限（默认 200 MB）和文件名合法性。
3. 系统在接收上传数据的同时加密，密文写到临时密文文件；内存只保留当前块，不落明文临时文件。
4. 加密完成后原子改名到最终随机路径，写入内容记录和加密的文件名/类型/校验值。
5. 数据库保存失败或上传中断时，删除本次产生的密文临时文件；旧内容不受影响。
6. 成功后在条目详情显示“已加密”“原始大小”“上传时间”，不显示明文内容。
7. 替换文件时，新内容保存成功后才删除旧的密文文件；删除失败写日志，留给清理命令处理。

### 6.6 查看文字秘密

1. 被授权用户打开文字条目。
2. 系统先检查条目未删除、未归档、账号启用、仍有授权、保险箱已解锁。
3. 页面显示网址、账号、秘密备注；密码显示为圆点。
4. 点击“显示密码”：调用独立接口，返回密码并写“显示密码”日志。
5. 点击“复制密码”：复制到剪贴板并写“复制密码”日志；不把密码写进日志或页面地址。
6. 未授权或已删除条目返回 404；保险箱锁定返回 423，不返回任何字段。

### 6.7 下载文件

1. 被授权用户打开文件条目，点击“下载/解密”。
2. 系统逐项检查权限和保险箱状态。
3. 系统先完整验证密文认证标签；失败则拒绝下载并记录完整性错误。
4. 验证通过后，边解密边把文件流式发送给浏览器；不在服务器生成明文临时文件。
5. 下载使用解密后的原始文件名（已清理危险字符），并提示“下载后文件将离开系统保护”。
6. 写“文件下载”日志，记录用户、条目编号、大小、结果；不记录文件内容或原始文件名。

### 6.8 回收站

1. 管理员点击“删除”，确认后条目进入回收站；普通用户立即看不到。
2. 管理员在“回收站”筛选里看到已删除条目，可点击“恢复”。
3. 恢复后保留原来的授权和内容，普通用户重新可见（如果未归档）。
4. 超过 30 天的条目由系统清理：删除密文文件、内容记录、授权和条目记录；写清理日志。
5. 清理后不可恢复；主密码丢失的情况下也不能恢复。

### 6.9 撤销权限与停用账号

- 撤销组/个人授权、移出组、停用账号后，下一次内容请求立即失败。
- 已经下载到用户电脑上的文件无法收回；系统只能通过留痕和制度约束降低风险。
- 已解锁的主密钥仍在服务器内存中，但不会绕过某条内容的授权检查。

### 6.10 完整性失败

- 密文被改动、截断、文件丢失、校验值不符时，系统拒绝返回内容。
- 日志记录条目编号和错误类型，不记录密文片段或明文。
- 管理员看到“内容损坏或被篡改，请联系维护者”，不要提供“忽略错误继续下载”的选项。

## 七、API 设计（初稿）

所有接口使用 `/api/v1/` 前缀；状态变更要求 CSRF；未登录 401；无权限 403（普通用户访问未授权内容用 404）。

### 7.1 保险箱状态与解锁

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/vault/status/` | 是否已初始化、是否已解锁；登录用户可看 |
| POST | `/api/v1/vault/initialize/` | 管理员设置主密码并生成主密钥；仅首次可用 |
| POST | `/api/v1/vault/unlock/` | 管理员输入主密码解锁；限速 |
| POST | `/api/v1/vault/lock/` | 管理员手动锁定，清空内存中的主密钥 |

### 7.2 管理员：内容管理

| 方法 | 路径 | 说明 |
|---|---|---|
| PUT | `/api/v1/admin/items/{id}/content/text/` | 创建或更新文字内容 |
| POST | `/api/v1/admin/items/{id}/content/file/` | 上传/替换文件（multipart） |
| DELETE | `/api/v1/admin/items/{id}/content/` | 清空内容（保留条目；第 5 阶段再开放） |
| POST | `/api/v1/admin/items/{id}/trash/` | 删除到回收站 |
| POST | `/api/v1/admin/items/{id}/restore/` | 从回收站恢复 |

### 7.3 被授权用户：读取内容

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/items/{id}/content/text/` | 返回网址、账号、秘密备注和“是否有密码”；不返回密码 |
| POST | `/api/v1/items/{id}/content/text/reveal/` | 返回密码；写日志 |
| POST | `/api/v1/items/{id}/content/text/copy-audit/` | 前端复制成功后调用；只写日志，不返回内容 |
| GET | `/api/v1/items/{id}/content/file/` | 验证后流式下载解密文件 |

### 7.4 状态码与响应规则

- 保险箱未初始化：内容相关操作返回 409 + `code=vault_not_initialized`。
- 保险箱未解锁：返回 423 + `code=vault_locked`，不返回内容字段。
- 主密码错误：400 + `code=invalid_master_password`；连续失败限速。
- 未授权/已删除/已归档：普通用户统一返回 404，不泄露存在性。
- 内容损坏：409 + `code=content_integrity_failed`。
- 文件过大：413 + `code=file_too_large`，提示上限。
- 磁盘空间不足：507 + `code=insufficient_storage`；不产生成功记录。
- 所有内容响应使用 `Cache-Control: no-store`，禁止浏览器/代理缓存。
- 下载响应使用安全的 `Content-Disposition`，清理文件名中的路径分隔符、控制字符和换行。
- 响应不包含数据钥匙、主密钥、密文路径或内部异常堆栈。

## 九、安全要求

| 编号 | 要求 | 说明 |
|---|---|---|
| S4-01 | 标准算法 | 只使用 AES-256-GCM 和成熟库，不自创加密算法、填充或随机数生成器 |
| S4-02 | 信封加密 | 每条内容独立数据钥匙；数据钥匙用主密钥包裹；主密钥不与密文同库存放 |
| S4-03 | 主密码不落盘 | 主密码不保存在数据库、`.env`、日志、备份说明的明文里 |
| S4-04 | 主密钥保护 | 主密钥只在解锁后存在内存；文件权限限制；不进 Git/静态目录 |
| S4-05 | 无明文临时文件 | 上传、加密、下载过程不在服务器磁盘生成明文临时文件 |
| S4-06 | 分块处理 | 文件按固定大小分块加解密，内存占用有上限 |
| S4-07 | 完整性 | GCM 认证标签 + 明文 SHA-256；篡改/截断/丢失时拒绝返回 |
| S4-08 | 逐次鉴权 | 每次查看、显示密码、复制、下载都重新检查账号状态和授权 |
| S4-09 | 不泄露存在性 | 普通用户未授权、已删除、已归档内容统一 404 |
| S4-10 | 管理员边界 | 管理员不看授权就不能解密内容；显式自授权写日志 |
| S4-11 | 解锁保护 | 解锁限速、错误不区分具体原因、失败写日志；不返回主密码是否正确以外的信息 |
| S4-12 | 日志脱敏 | 不记录主密码、数据钥匙、明文、密码字段、文件内容、原始文件名 |
| S4-13 | 文件名安全 | 原始文件名加密；下载时清理路径穿越、控制字符、超长文件名 |
| S4-14 | 大小限制 | 默认 200 MB，可配置；服务端强制执行，不能只靠前端 |
| S4-15 | 失败清理 | 上传中断、数据库失败、磁盘写满时清理本次临时密文，不留下“成功”记录 |
| S4-16 | 回收站保护 | 删除不立即销毁；到期清理写日志；恢复保留原授权 |
| S4-17 | CSRF | 初始化、解锁、内容修改、删除、复制留痕都校验 CSRF |
| S4-18 | 缓存 | 内容响应和下载响应禁止缓存；错误页不包含秘密 |
| S4-19 | 依赖安全 | 锁定加密库版本；开源前扫描漏洞和密钥 |
| S4-20 | 密钥备份 | README/界面说明“数据库 + 密文 + 主密钥文件 + 主密码”四者缺一不可 |

### 信任模型说明

第 1 版是服务器端加密：

- 服务器解锁后，拥有服务器最高权限的恶意管理员理论上可以从内存或进程取得主密钥；
- 本阶段主要防止：硬盘/备份被单独偷走、普通用户越权、管理员默认全量可见、误操作；
- 不能宣传“连恶意服务器管理员也看不到”；要防住这一点，需要后续端到端加密；
- 如果选了 D4-1 B（钥匙文件常驻本机），连“整台电脑被偷”也防不住，必须在文档和界面中明确。

## 十、数据库迁移方案

### 10.1 迁移前

1. 停止后端服务，确认没有写入。
2. 数据库完整性检查。
3. 备份到 `data/backups/stage3-before-content-YYYYMMDD-HHMMSS/`。
4. 记录迁移前账号数量、用户名校验值、角色、启用状态、条目数量、组/授权数量；不记录明文密码或内容。
5. 确认备份可打开。

### 10.2 迁移

- 新增 `VaultContent` 表。
- 给 `VaultItem` 增加 `is_deleted`、`deleted_at`、`deleted_by` 字段。
- 不自动生成密钥，不修改现有账号、组、授权、条目标题/说明。
- 不删除任何第 3 阶段数据。

### 10.3 迁移后验证

- 账号数量、密码校验值、角色、启用状态不变。
- 组、成员、条目、授权数量不变。
- 第 1–3 阶段测试和登录、用户管理、组授权功能仍正常。
- 新表存在；旧数据完整；失败时按备份回退。

### 10.4 回退

- 停止服务；
- 将新数据库移到一边（不删除）；
- 从备份恢复；
- 恢复第 3 阶段代码并验证账号可登录；
- 本阶段新增的密文文件如果尚未产生，不需要处理；如果已产生，保留文件并记录，不手动删除。

## 十一、验收标准

### 11.1 数据安全与兼容

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC4-01 | 保留现有账号 | 迁移前后账号数量、密码校验值、角色、启用状态一致 |
| AC4-02 | 保留第 3 阶段数据 | 组、成员、条目、授权数量和关系不变 |
| AC4-03 | 占位条目 | 旧占位条目仍可打开，显示“尚未添加内容”；可补充内容 |
| AC4-04 | 增量迁移 | 没有重建数据库；迁移前备份存在且可打开 |

### 11.2 主密钥与解锁

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC4-05 | 首次初始化 | 管理员设置主密码后生成主密钥文件；文件中没有明文主密钥或主密码 |
| AC4-06 | 主密码确认 | 两次输入不一致、少于 12 位时拒绝 |
| AC4-07 | 错误主密码 | 不能解锁；提示统一；连续失败被限速；日志无主密码 |
| AC4-08 | 重启后锁定 | 重启服务后内容操作返回 423；正确主密码解锁后恢复 |
| AC4-09 | 普通用户解锁 | 普通用户不能调用解锁接口，返回 403 |
| AC4-10 | 主密码丢失 | 文档和界面明确说明无法恢复；没有隐藏后门或跳过方式 |

### 11.3 文字秘密

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC4-11 | 保存文字秘密 | 网址、账号、密码、秘密备注加密保存；数据库中找不到这些明文 |
| AC4-12 | 查看文字 | 被授权用户能看到网址、账号、备注；密码默认不返回 |
| AC4-13 | 显示密码 | 点击后返回密码；写“显示密码”日志；日志无密码 |
| AC4-14 | 复制密码 | 写“复制密码”日志；日志无密码 |
| AC4-15 | 编辑文字 | 保存后重新加密；新值正确；密码留空保持原密码 |
| AC4-16 | 未授权文字 | 普通用户访问返回 404；不返回是否存在 |
| AC4-17 | 管理员无授权 | 管理员可以看标题，但内容接口返回 404 |

### 11.4 文件

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC4-18 | 上传加密 | 上传成功后磁盘上无明文、无原始文件名、无原后缀 |
| AC4-19 | 下载还原 | 下载文件与上传文件 SHA-256 一致；原始文件名恢复正确 |
| AC4-20 | 权限判断 | 未授权、停用、撤销后不能下载；每次请求重新校验 |
| AC4-21 | 完整性 | 手动篡改密文后拒绝下载并提示损坏；正常文件通过 |
| AC4-22 | 大小限制 | 超过上限被拒绝；恰好在上限内的文件成功 |
| AC4-23 | 无明文临时文件 | 上传和下载过程中服务器临时目录没有明文文件 |
| AC4-24 | 大文件 | 至少 20 MB 文件加解密成功且内存占用可控；有条件的验收再用接近 200 MB 的文件 |
| AC4-25 | 路径安全 | 恶意文件名（`../`、控制字符、超长）不能写到数据目录外 |
| AC4-26 | 磁盘写满/中断 | 上传失败后没有成功记录，本次临时密文被清理，旧数据不受损 |
| AC4-27 | 替换文件 | 新文件成功后才删除旧密文；失败时旧文件仍可下载 |

## 十三、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 主密码丢失 | 所有内容永久无法解密 | 首次设置强制确认；界面反复警告；README 写明离线保存；备份材料四件套 |
| 主密钥文件丢失/损坏 | 同上 | 迁移/初始化后提示立即备份；第 7 阶段加密备份包含密钥材料 |
| 整盘被偷（若选 D4-1 B） | 钥匙与密文一起泄露 | 明确写进文档和界面；推荐 A；建议 BitLocker 作为第二层 |
| 服务器被攻破且已解锁 | 主密钥在内存，攻击者可解密 | 无法在服务器端加密下完全避免；限制服务器权限、及时锁定、后续 E2E |
| 明文临时文件 | 磁盘残留秘密 | 自定义流式上传处理器，只写密文临时文件；测试检查 |
| 大文件内存/磁盘 | 服务卡顿、上传失败 | 分块流式；200 MB 上限；磁盘空间预检查；失败清理 |
| 密文损坏/篡改 | 用户拿到错误内容 | GCM + SHA-256；下载前验证；失败拒绝 |
| 文件名/路径攻击 | 写到数据目录外或覆盖文件 | 随机内部文件名；原始文件名只做加密元数据；下载时清理；绝不拼接用户路径 |
| 管理员自授权 | 管理员可显式获得内容 | 写日志；文档说明信任模型；后续可升级 E2E |
| 加密库漏洞 | 机密性受损 | 锁定版本、关注安全公告、开源前扫描 |
| 回收站清理误删 | 数据无法恢复 | 30 天保留；清理写日志；先备份；不提供静默清理 |
| 范围膨胀 | 第 4 阶段拖长 | 只做内容加密引擎和基础界面；分类/标签、完整 Web、审计 UI、备份 UI 后续 |

### 16.2 已实现功能

**密钥与解锁**

- 使用 `cryptography==50.0.2` 提供 AES-256-GCM。
- 主密码通过 Argon2id 派生开锁钥匙；主密钥文件 `data/keys/master.key.json` 只保存“被包裹的主密钥”、盐和 KDF 参数。
- 主密钥只在解锁后存在内存；服务器重启后自动锁定。
- 管理员可以设置主密码、解锁、手动锁定；普通用户不能调用这些接口。
- 解锁接口限速；错误主密码返回统一提示，不记录主密码。
- 主密码丢失无法恢复；界面和文档都有明确警告。

**文字与文件加密**

- 每条内容生成独立的 256 位数据钥匙；数据钥匙用主密钥包裹后存数据库。
- 文字内容（网址、账号、密码、秘密备注）作为整体加密，存数据库密文。
- 文件使用分块流式 AES-256-GCM：接收上传数据时立即加密，只写密文临时文件；完成后原子移动到 `data/vault/objects/<随机编号>.vault`。
- 自定义上传处理器避免 Django 默认的明文临时文件。
- 原始文件名和 MIME 类型加密保存；磁盘文件名随机且无原后缀。
- GCM 认证标签 + 明文 SHA-256 双重完整性校验；下载前先完整验证，篡改或截断时拒绝返回。
- 文件大小默认上限 200 MB，可由 `VAULT_MAX_FILE_SIZE_MB` 调整；超限返回 413 并清理本次临时密文。
- 文件名清理路径分隔符、控制字符和超长内容；下载使用安全的 `Content-Disposition`。
- CORS 暴露 `Content-Disposition`，前端能恢复原始文件名。

**权限与审计**

- 查看文字、显示密码、复制密码、下载文件都重新检查账号状态、条目标题/归档/回收站状态和有效授权。
- 普通用户未授权、已归档、已删除内容统一返回 404。
- 管理员可以看到元数据，但不会自动获得内容权限；内容接口同样要求所有者/授权。
- 管理员可以给空条目添加内容；编辑/替换已有内容需要内容访问授权，避免在看不到原文的情况下覆盖别人的秘密（实现差异见 16.4）。
- 显示密码、复制密码、文件下载、内容保存、解锁、删除、恢复都写安全日志；日志不含明文、密码、主密码、数据钥匙或原始文件名。

**回收站**

- 支持删除到回收站、恢复；普通用户立即看不到。
- 默认保留 30 天；管理员打开条目列表时按小时触发一次过期清理，同时提供 `manage.py purge_trash` 命令。
- 清理会删除内容记录、授权、条目和密文文件，并写日志。
