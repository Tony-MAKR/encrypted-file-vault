## 一、本阶段目标

1. 建立可持续运行的自动化测试：后端、前端、桌面端，以及（可选）浏览器端到端测试。
2. 增加 GitHub Actions 持续集成，每次提交自动跑测试、构建和代码检查。
3. 确定并加入开源许可证；检查第三方依赖许可证是否兼容。
4. 补齐开源项目文档：中文 README、英文 README、贡献指南、行为准则、安全策略、变更日志、发布说明。
5. 做一次发布前安全检查：依赖漏洞、密钥/真实数据扫描、Git 历史检查。
6. 制定版本发布流程：版本号、构建产物、SHA-256、GitHub Release 草稿和回滚说明。
7. 准备 GitHub 仓库文件：Issue 模板、Pull Request 模板、依赖更新配置。
8. 保持第 1–7 阶段功能不变；不修改数据库、密钥、授权和加密格式。

## 三、需要你拍板的关键决定

### 3.1 D8-1：使用哪种开源许可证？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. Apache-2.0（推荐）** | 一张宽松的“社区通行证”，别人可以自由使用、修改、商用，但要保留版权和许可证声明 | 开源社区最常见、企业容易接受；包含专利授权；对贡献者友好；适合长期传播 | 不强制别人公开修改后的代码；不能阻止闭源的商业分支 |
| B. AGPL-3.0 | 更严格的“公共使用协议”：谁把修改后的版本作为网络服务提供，也必须公开源码 | 能防止别人拿你的代码做闭源在线服务；更符合“公共基础设施”理念 | 一些公司会避免使用 AGPL；使用和分发限制更多；解释成本更高 |
| C. MIT | 最短、最宽松的许可证，几乎只要求保留版权声明 | 最简单、最容易被人采用 | 没有明确的专利授权条款；保护力度最弱 |

**推荐：A（Apache-2.0）。**

说明：

- 这个项目是自托管的本地/局域网工具，Apache-2.0 足够保护版权，也方便别人使用和贡献。
- Apache-2.0 含专利授权条款，对安全类项目更稳妥。
- 如果你更在意“别人改了代码提供在线服务必须开源”，可以选 B；我会改用 AGPL-3.0，并在 README 里说明。
- 许可证是法律文件；正式商用或大规模分发前，建议咨询专业人士。本项目按“原样提供、不承担担保”发布。

### 3.2 D8-2：自动化测试做到什么程度？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| A. 保留现有测试 + CI，浏览器验收按文档手动做 | 已有的 161 个后端测试、前端构建和桌面单元测试全部自动跑；浏览器验收由人按清单点一遍 | 稳定、依赖少、CI 快；维护成本低 | 页面被改坏时，CI 不一定能发现 |
| **B. 在 A 的基础上增加少量 Playwright 浏览器测试（推荐）** | 再请一个“自动点网页的机器人”，每次提交自动走登录、授权、审计、备份等关键流程 | 能发现页面和接口联动的问题；开源贡献者改前端时更有保障；测试可重复 | 新增一个浏览器测试依赖；CI 需要下载浏览器；测试选择器和等待逻辑需要维护 |
| C. 只做手动测试 | 每次发布前人工点一遍 | 工作量最小 | 无法持续保证质量；开源后别人改代码容易引入回归 |

**推荐：B（增加少量 Playwright 测试）。**

说明：

- 只覆盖最关键、最稳定的 4–5 条路径：首次设置/登录、普通用户看不到未授权内容、保存并查看文字秘密、审计查询、创建并验证备份。
- 不做“所有按钮都点一遍”的大而全测试，避免测试脆弱、维护成本高。
- 桌面 Electron 的安装/卸载仍然保留人工验收清单；不在 CI 中自动安装客户端。
- 如果你希望 CI 尽量简单，可以选 A，我会保留现有测试和手动验收文档。

### 3.3 D8-3：持续集成用哪个环境？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. GitHub Actions，Windows 环境（推荐）** | 每次提交，GitHub 自动开一台 Windows 机器跑测试 | 和实际使用环境一致；能跑 PowerShell、桌面测试和浏览器测试 | Windows 机器启动比 Linux 慢；公开仓库免费但消耗额度 |
| B. GitHub Actions，Ubuntu 环境 | 用 Linux 机器跑后端和前端测试 | 快、便宜、社区最常见 | 和目标 Windows 环境不完全一致；PowerShell 和桌面相关步骤要跳过或另跑 |
| C. 两种环境都跑 | Windows 和 Ubuntu 各跑一遍 | 覆盖最全 | 配置和维护成本最高；第一版没有必要 |

**推荐：A（Windows 环境）。**

说明：

- 这个项目明确面向 Windows 10/11；在 Windows 上跑测试最能发现问题。
- 公开仓库的 GitHub Actions 通常有免费额度；个人项目足够用。
- 桌面安装包不在每次提交时打包，只在发布标签时构建，避免每次 CI 都下载 Electron。
- 如果以后有 Linux 部署需求，再单独加任务。

### 3.4 D8-4：文档做成什么语言？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 中文 README 为主 + 英文 README 摘要（推荐）** | 主说明书用中文，另放一页英文简介和快速开始 | 你和中文用户看得懂；外国开发者能快速了解项目；维护量可控 | 英文文档不是逐字完整翻译 |
| B. 全部文档中英双语 | 每份文档都准备两个版本 | 对国际贡献者最友好 | 维护量翻倍；每次改动都要同步两份 |
| C. 只做中文 | 只服务中文用户 | 最简单 | 国际用户很难参与；不符合开源项目的常见做法 |

**推荐：A（中文为主 + 英文 README 摘要）。**

说明：

- 界面第一版仍是中文；完整操作文档先用中文，符合你的使用场景。
- 英文 README 包含项目简介、功能、安装、运行、安全边界和许可证，足够让外国开发者判断是否参与。
- 如果以后有国际用户，再逐步补英文完整文档。

### 3.5 D8-5：发布时提供哪些文件？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 安装包 + 免安装包 + SHA-256 + 源码（推荐）** | 像正规软件发布：给安装版、绿色版、校验值和源代码 | 普通用户和开发者都能用；便于核对文件；符合前几阶段交付 | 发布文件较大；需要每次构建和校验 |
| B. 只发布源代码 | 只给开发者 | 最轻量 | 普通用户无法直接安装；不满足桌面客户端的目标 |
| C. 只发布安装包 | 只给安装版 | 简单 | 没有免安装选择；无法核对源码和构建材料 |

**推荐：A（完整发布包）。**

说明：

- 发布到 GitHub Releases 的文件：安装版 `.exe`、免安装 `.zip`、`SHA256SUMS.txt`、`INSTALL.txt`，以及 GitHub 自动生成的源码包。
- 首个公开版本建议使用 `1.0.0`；如果你希望继续用 `0.x`，可以在确认时说“版本用 0.8.0”。
- 安装包仍未签名，Release 说明中要写清 SmartScreen 提示和校验方法。
- 不自动更新、不静默下载；升级仍是手动覆盖安装。

### 3.6 D8-6：什么时候把代码公开到 GitHub？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 本阶段只准备本地仓库和发布材料，由你手动创建仓库并推送（推荐）** | 把房子收拾好，钥匙交给你，什么时候开门由你决定 | 你完全控制公开时机；不会误推密钥或未完成内容；不需要把 GitHub 凭据交给我 | 需要你自己在 GitHub 点几下；推送前的最后检查由你确认 |
| B. 你提供 GitHub 登录后由我推送 | 我帮你开门 | 省事 | 需要授权和凭据；公开是不可逆的；出错影响大 |
| C. 本阶段不准备任何 GitHub 文件 | 继续本地开发 | 最简单 | 以后还要补一轮；不符合“开源发布”目标 |

**推荐：A（只准备，不自动推送）。**

说明：

- 代码公开后可能被缓存、索引和 fork，删除也不能完全撤回；应由你在最后检查后亲手按下发布。
- 我会准备好：
  - 许可证和所有文档；
  - GitHub Actions 工作流；
  - Issue/PR 模板；
  - 发布检查清单和 Release 说明草稿；
  - 本地完整测试结果。
- 你只需要创建空仓库、添加远程地址并推送；具体命令我会写在发布文档里。
- 如果你确认要我在你登录 `gh` 后推送，可以选 B；我会先做密钥扫描并再次向你确认。

### 3.7 D8-7：安全问题怎么接收和披露？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. SECURITY.md + GitHub 私密安全报告（推荐）** | 留一个“只给维护者看”的信箱和流程 | 不公开个人邮箱；漏洞细节不会立刻暴露；GitHub 原生支持 | 需要仓库公开后启用该功能；响应依赖你本人 |

| C. 让大家直接开公开 Issue | 有问题公开说 | 最省事 | 漏洞细节公开，可能在修复前被利用；**不推荐** |

**推荐：A（GitHub 私密安全报告）。**

说明：

- SECURITY.md 会写清支持版本、如何私密报告、预期响应时间（例如 7 天内确认）和不要公开细节。
- 不在文档里放你的真实邮箱；如果以后需要，可以再单独加。
- 本阶段不会做正式渗透测试；只做依赖扫描和发布前检查。

## 五、测试计划

### 5.1 后端测试

- 保留现有 161 个 pytest 测试。
- 增加覆盖率报告（`pytest-cov`），作为参考，不设强制百分比门槛。
- 覆盖重点：认证、会话、用户/组/授权、加密内容、回收站、审计、备份、恢复、安全检查。
- 每次 CI 运行 `pytest` 和 `ruff check .`。

### 5.2 前端测试

- `npm ci` 安装锁定依赖。
- `npm run build`：TypeScript 类型检查 + 生产构建。
- `npm run lint`：Oxlint。
- 不引入大型 UI 组件库或新的状态管理框架。

### 5.3 桌面测试

- `npm test`：地址校验、配置读写、健康检查、错误提示。
- `npm run smoke`（CI 可选）：Electron 设置页、主窗口、错误页在 Windows 上启动检查。
- 安装/卸载、下载对话框仍按人工验收清单执行。

### 5.4 浏览器端到端测试（若选 D8-2 B）

使用 Playwright + Microsoft Edge（Chromium 内核），只覆盖 5 条核心路径：

| 编号 | 路径 | 检查点 |
|---|---|---|
| E2E-1 | 首次设置和登录 | 创建管理员、登录、进入主页 |
| E2E-2 | 权限隔离 | 普通用户看不到未授权内容；管理员能看到管理页面 |
| E2E-3 | 文字秘密 | 管理员初始化保险箱、保存文字内容；授权用户可以查看和显示密码 |
| E2E-4 | 审计 | 登录、查看、授权等操作出现在审计页面，可按条件筛选 |
| E2E-5 | 备份 | 创建备份、验证通过、备份和验证出现在审计记录中 |

测试环境：

- 启动前在临时目录执行数据库迁移，使用独立 `DATA_DIR` 和独立端口（例如 8020）。
- 测试结束后删除临时数据，不接触真实数据库和密钥。
- Playwright 配置不自动重试成功用例；失败时保留截图和跟踪文件（不包含密码）。

### 5.5 发布前人工验收

保留并更新现有验收清单，至少包括：

- 全新安装、首次设置、登录、退出。
- 创建用户/组、授权、撤销。
- 文字秘密保存、查看、显示/复制密码。
- 文件上传、下载、回收站、永久删除。
- 审计筛选和详情。
- 备份创建、验证、命令行恢复演练。
- 桌面安装包安装、启动、卸载；卸载后服务器数据仍在。
- 升级覆盖安装后服务器地址设置保留。

### 5.6 安全检查

| 检查 | 工具/方法 | 通过标准 |
|---|---|---|
| Python 依赖漏洞 | `pip-audit` | 无高危/严重漏洞；中危有说明 |
| 前端依赖漏洞 | `npm audit --omit=dev` | 运行时依赖无高危/严重漏洞 |
| 桌面依赖漏洞 | `npm audit` | 记录构建期依赖情况；运行时无高危 |
| 密钥/隐私扫描 | `gitleaks` 或等效工具 | 当前文件和 Git 历史中没有真实密钥、密码、个人数据 |
| Django 部署检查 | `manage.py check --deploy` | 记录并解释警告 |
| 安全自检命令 | `manage.py security_check` | 无失败项 |

- 如果发现真实密钥或数据进入了 Git 历史，**先停下来告知你**；修改历史是破坏性操作，必须取得你的同意后再做。
- 依赖漏洞修复优先升级版本；不能升级的，记录风险和处理计划。

## 六、持续集成设计

### 6.1 工作流

文件：`.github/workflows/ci.yml`（若选 Windows）。

触发：

- 推送到 `main`；
- 所有 Pull Request；
- 手动触发（`workflow_dispatch`）。

任务：

1. **backend**：安装 Python 依赖，运行 `pytest`、`ruff check .`。
2. **frontend**：`npm ci`、`npm run build`、`npm run lint`。
3. **desktop**：`npm ci`、`npm test`。
4. **e2e**（若选 B）：使用 Windows runner 自带的 Microsoft Edge（Chromium 内核），启动临时服务器，运行核心流程。
5. **security**（可选独立任务）：`pip-audit`、`npm audit`、密钥扫描。
