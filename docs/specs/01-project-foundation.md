## 一、本阶段目标

把后续所有功能都要依赖的“地基”做扎实：

1. 建立一个干净的项目骨架，分为后端、前端、文档、脚本、数据目录。
2. 后端能启动，提供一个健康检查接口。
3. 前端能启动，能调用后端健康检查并显示结果。
4. 配置与密钥不写死在代码里，真实 `.env` 不进版本库。
5. 数据库能连接、能执行迁移，为第 2 阶段的用户表打好基础。
6. 日志能落盘、能轮转、自动隐藏密码/令牌等敏感字段。
7. 安全基线到位：只监听本机、限制跨域、错误信息不泄露内部细节、依赖版本锁定。
8. 有自动化测试和一份照着做就能启动的 README。
9. 本阶段结束提供可演示版本，你确认后再进入“账号与角色”阶段。

## 三、需要你确认的技术选型

你已确认“Python 后端 + React 网页”的大方向，但“具体用哪个 Python 框架、哪个数据库”还没定。下面用生活化方式对比，**推荐项不是已经替你决定，等你点头才动手**。

### 3.1 后端框架

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. Django 5.2 LTS + Django REST Framework（推荐）** | 一套精装修房子：门锁、水电、保安、账本都自带，拎包入住 | 自带账号、密码哈希、会话、权限、跨站请求伪造防护、数据库迁移；LTS 长期支持到 2028 年；社区大、资料多；安全默认值更完整 | 结构更“重”，需要按它的规矩写；默认后台界面不适合直接当成品，仍需 React 前端；学习曲线比 FastAPI 稍陡 |
| **B. FastAPI** | 毛坯房 + 一套高质量工具箱：很轻、很快，但门窗要自己装 | 接口开发快、自动生成接口文档；代码轻量清晰；异步性能好 | 账号、会话、跨站请求伪造、权限等安全组件要自己组装，代码更多，出错面更大；长期维护需要更多自建约定 |
| **C. Flask** | 自己搭棚子：最自由，也最费心 | 极简、灵活、容易上手 | 安全、账号、权限、迁移几乎都要自己搭；对本项目不推荐 |

**推荐：A（Django 5.2 LTS + DRF）。**

理由：

- 本项目是“带账号、角色、权限、审计的管理系统”，Django 已经把这些最容易出安全事故的基础件做好了。
- 它是 LTS（长期支持版），适合长期项目；官方文档确认 Django 5.2.8 起支持你电脑上的 Python 3.14。
- 我们仍然用 React 做界面，不启用 Django 自带的默认后台，避免多一个暴露面。
- 如果安装时发现 Django REST Framework 与 Python 3.14 有兼容问题，我会**停下来向你报告**，不会擅自换框架。

### 3.2 数据库

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. SQLite（推荐）** | 一个文件就是整个数据库，像一本带锁的账本 | 不用安装额外服务；备份简单；单机、小团队足够；Django 原生支持；以后可通过 ORM 迁移到 PostgreSQL | 同一时间只允许一个写入者；不适合多台服务器同时写；数据量大/并发高时需要升级 |
| **B. PostgreSQL** | 专业仓库 + 专职管理员 | 并发强、功能全、适合未来多机/云端；备份和权限体系成熟 | 需要在 Windows 上单独安装和维护一个数据库服务；对第一版单机小团队偏重，增加你的运维负担 |

**推荐：A（SQLite）。**

理由：第一版是单机、局域网、50 个账号以内、10 人左右同时在线，SQLite 完全够用；它让备份和部署简单很多。代码会通过 Django ORM 访问数据库，未来如果用户量明显增长，可以在我单独写迁移 spec 后切换到 PostgreSQL，不需要重写业务逻辑。

## 六、配置与密钥

### 6.1 配置文件

- 使用项目根目录的 `.env` 保存开发环境配置；`.env` **绝对不进 Git**。
- 提供 `.env.example`，只写变量名和占位值，不写真实密码。
- 必填项缺失或明显不安全时，后端**拒绝启动**，并给出中文提示。
- 生产环境使用系统环境变量，不依赖 `.env` 文件。

### 6.2 关键配置项（初稿）

| 配置 | 用途 | 本阶段默认 |
|---|---|---|
| `DJANGO_SECRET_KEY` | Django 会话/签名密钥 | 首次安装自动生成随机值；不得提交 |
| `DJANGO_DEBUG` | 调试模式 | 开发环境 true；默认安全值 false |
| `DJANGO_ALLOWED_HOSTS` | 允许访问的域名 | 仅 `127.0.0.1,localhost` |
| `DATA_DIR` | 数据根目录 | 项目下 `data/` |
| `FRONTEND_DEV_ORIGIN` | 开发时前端地址 | `http://127.0.0.1:5173` |
| `LOG_LEVEL` | 日志级别 | 开发 INFO，生产 INFO/WARNING |

### 6.3 密钥原则

- 主密钥、加密密钥、备份口令**不在本阶段生成**；第 4、7 阶段再按各自 spec 处理。
- 本阶段只处理 Django 自身的 `SECRET_KEY`；它不等于未来的文件加密主密钥。
- 所有密钥都不写进代码、不写进日志、不写进 README、不提交到 Git。
- 数据目录不放在前端静态目录下，不能被浏览器直接访问。

## 七、数据库与迁移

- 数据库文件：`data/db/db.sqlite3`，由 Django 管理。
- 本阶段只执行 Django 内置迁移（账号、会话等基础表），**不创建用户/组/条目等业务表**。
- 启用 SQLite 的关键设置：WAL 模式、外键约束、合理的等待超时，降低并发读写冲突。
- 所有数据库结构修改必须通过迁移文件完成，禁止手改数据库结构。
- 迁移前备份策略在第 2 阶段开始真正生效；本阶段没有业务数据，但仍禁止删除或覆盖已有文件。
- 第 2 阶段会在本骨架上新增用户、角色等表。

## 八、日志与审计基础

本阶段只做“技术日志”，业务审计日志（谁看了什么）在第 7 阶段实现。

要求：

1. 日志写到 `data/logs/app.log`，按大小轮转，保留有限份数，避免磁盘被塞满。
2. 开发时同时输出到终端，方便排查。
3. 每条请求带请求编号，便于把前端报错和后端日志对应起来。
4. 自动隐藏敏感字段：`password`、`secret`、`token`、`key`、`authorization`、`cookie` 等。
5. 不记录请求体中的密码、文件内容；不记录完整 Cookie。
6. 错误日志不输出密钥、数据库路径以外的内部细节给前端；详细堆栈只写本地日志。
7. 日志目录在 `data/` 下，不进 Git，不通过网页暴露。

## 九、安全基线

本阶段交付的安全措施：

| 措施 | 具体做法 |
|---|---|
| 监听范围 | 后端开发服务器只绑定 `127.0.0.1`，不监听所有网卡；避免第一阶段误暴露到局域网 |
| 跨域限制 | 只允许开发前端地址访问 API；不使用 `*` 通配 |
| 安全响应头 | 禁止 MIME 嗅探、禁止被 iframe 嵌入、限制 Referrer、关闭不必要的浏览器能力 |
| 错误处理 | API 返回统一 JSON 错误；生产模式不返回堆栈、路径、配置 |
| 数据库 | 数据库文件不在静态目录；启用 WAL/外键；不使用默认空密码（SQLite 无账号口令，靠文件权限 + 全盘加密） |
| 依赖 | 运行依赖锁定版本；安装后执行一致性检查；不使用来源不明的包 |
| 密钥 | 缺密钥拒绝启动；密钥不进代码/仓库/日志 |
| CORS | 白名单，仅开发地址 |
| HTTPS | 本阶段不做局域网访问；后续局域网部署时必须加 HTTPS，单独在阶段 7 验证 |
| 权限 | 本阶段没有业务权限；不提前开放管理接口 |

> 本阶段结束时，系统**只能在本机访问**。这是刻意的安全限制，不是功能缺失。真正对局域网开放要等登录、权限、HTTPS 都做好之后。

## 十、前后端连通方式

- 后端 API 前缀：`/api/v1/`。
- 健康检查：`GET /api/v1/health/`。
- 返回内容示例（不含敏感信息）：

```json
{
  "status": "ok",
  "database": "ok",
  "version": "0.1.0"
}
```

- 数据库异常时返回 HTTP 503，`status` 为 `degraded`，不返回数据库路径或错误堆栈。
- 前端占位页显示：
  - 项目名称与当前阶段；
  - “后端连接：正常/异常”；
  - 当前版本；
  - 明确提示“本阶段尚无登录和文件功能”。

## 十一、测试与验收标准

### 11.1 自动测试

- 后端：健康接口返回 200 且数据库状态为 ok；数据库故障时返回 503；缺少关键配置时启动失败并给出提示。
- 日志：写入一个包含 `password=...` 的测试日志，文件中不应出现原始密码。
- 安全头：响应包含约定的安全头；CORS 只允许开发地址。
- 前端：`npm run build` 成功；占位页能渲染。
- 依赖：`pip check` 通过；依赖版本已锁定。

### 11.2 手动验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-1 | 全新安装 | 在项目目录执行安装脚本，能自动创建虚拟环境、安装依赖、生成 `.env`、完成数据库迁移 |
| AC-2 | 启动后端 | 后端只监听 127.0.0.1；访问健康接口返回 200 |
| AC-3 | 启动前端 | 前端打开后显示占位页，并显示“后端连接：正常” |
| AC-4 | 配置安全 | 删除或改坏 `DJANGO_SECRET_KEY` 后，后端拒绝启动并提示修复方法 |
| AC-5 | 仓库安全 | `.env`、`data/`、`.venv/`、`node_modules/` 都没有被 Git 跟踪；仓库里搜不到真实密钥 |
| AC-6 | 日志 | 日志文件生成；包含请求编号；测试密码被替换为 `***`；轮转配置生效 |
| AC-7 | 数据目录 | 数据库位于 `data/db/`；无法通过浏览器 URL 直接下载数据库文件 |
| AC-8 | 跨域 | 只允许配置的前端地址；从其他来源请求被拒绝 |
| AC-9 | 自动化测试 | `pytest` 全部通过；前端构建通过 |

## 十三、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Python 3.14 与 Django/DRF 的兼容性 | 依赖装不上或运行异常 | 使用 Django 5.2.8+；先做安装与启动验证；有阻止性问题就停下来报告，不擅自换框架 |
| Windows 路径/权限差异 | 脚本或数据目录出错 | 使用跨平台路径写法；在 Windows 11 上实际跑通再交付 |
| 开发服务器误暴露到局域网 | 未登录状态被外部访问 | 只绑定 127.0.0.1；文档明确警告；不提供 `0.0.0.0` 启动脚本 |
| 日志泄露敏感信息 | 密码/令牌落盘 | 脱敏过滤器 + 测试；日志目录不进 Git；不记录请求体 |
| 依赖供应链风险 | 引入恶意/有漏洞的包 | 只用主流包、锁定版本、`pip check`、后续加漏洞扫描 |
| 范围膨胀 | 地基阶段拖太久 | 本 spec 明确“不做什么”；新需求进入后续阶段 |
| Git 提交包含敏感文件 | 密钥/数据进版本库 | 先写 `.gitignore`，提交前扫描；`.env` 和 `data/` 从不跟踪 |
| 前端/后端跨域配置错误 | 页面调不通接口 | 只允许开发地址；用健康接口做端到端验收 |
