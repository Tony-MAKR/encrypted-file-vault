## 一、本阶段目标

1. 管理员可以创建、修改、删除用户组，并管理组成员。
2. 一个用户可以属于多个组；组和用户都可以被授权访问某条内容。
3. 建立内容条目（文件/文字）的**元数据**和授权关系，但**暂不保存真实内容**。
4. 实现统一的“有效权限”计算：上传者、直接授权、组授权三者取并集。
5. 撤销授权、移出用户组、停用账号后，权限立即失效。
6. 提供管理员的分组管理、条目管理和授权界面，以及普通用户的“我能看到的内容”列表。
7. 保留第 2 阶段的全部账号和登录能力；使用新增迁移，不重置数据库。
8. 为第 4 阶段的加密文件/文字内容打好权限基础。

## 三、需要你拍板的关键决定

### 3.1 D3-1：本阶段的范围

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 用户组 + 条目元数据 + 授权（推荐）** | 先建好门禁和房间号，房间里的家具下一阶段再搬 | 现在就能完整验证“谁能看到哪条内容”；授权逻辑可在加密功能加入前先测住 | 条目暂时只有标题和权限，没有真实文件/文字内容；页面会明确标注“占位” |
| **B. 只做用户组，不做条目授权** | 只装门禁，不建房间 | 本阶段代码少、风险低 | 无法端到端验证授权；第 4 阶段会同时承担条目、授权和加密，压力更大 |
| **C. 合并第 3、4 阶段，一次做组+条目+加密** | 一次把房子装修完 | 完成后就是完整可用的功能 | 单阶段工作量明显变大，评审和排错更困难，不符合“小步验收”的节奏 |

**推荐：A（用户组 + 条目元数据 + 授权）。**

说明：

- “条目元数据”指标题、类型（文件/文字）、说明、上传者、授权对象等管理信息，不包含真实文件内容或密码明文。
- 这一阶段可以真实测试“普通用户只看到被授权的条目标题”“移出组后看不到”“个人授权和组授权并存”等核心规则。
- 第 4 阶段再把真实加密内容接入同一条条目；不会推倒重来。

### 3.2 D3-2：用户组是否支持嵌套？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 平铺组（推荐）** | 一组并列的部门，例如“财务组”“运维组” | 规则简单、好理解；一个用户可加入多个组；权限结果容易预测 | 如果有“部门下面再分小组”的复杂组织，需要多建几个组 |
| **B. 嵌套组** | 部门树，父组的权限自动传给子组 | 组织层级复杂时少配一些授权 | 继承、循环、删除和排错都更复杂；容易出现“为什么他能看”的困惑 |

**推荐：A（平铺组）。**

第一版的小团队规模用平铺组足够；以后确有需要，再单独设计嵌套或部门树，不提前增加复杂度。

### 3.3 D3-3：删除一个已经授权过内容的用户组，怎么处理？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 有授权时禁止删除（推荐）** | 柜子里还有别人的取件授权，先清点再拆柜 | 不会因为删组导致一批人突然失去访问；管理员必须先明确撤销授权 | 删除前多一步清理；界面会提示先处理哪些条目 |
| **B. 删除组并自动撤销所有组授权** | 直接拆柜，相关取件权一起作废 | 操作快 | 可能让一批用户突然看不到内容，容易误操作 |
| **C. 软删除/归档组** | 把组收进仓库，不再分配新权限 | 保留历史，风险低 | 多一层状态和恢复逻辑；第一版收益有限 |

**推荐：A（有授权时禁止删除）。**

如果组没有关联授权，可以删除；删除时清理组成员关系。只要有任意条目还授权给这个组，就拒绝删除并提示先撤销；这比“悄悄让一批人失去访问”更安全。

### 3.4 D3-4：谁可以给条目配置授权？

| 选项 | 像什么 | 优点 | 缺点 |
|---|---|---|---|
| **A. 任意管理员都可以管理授权（推荐）** | 每个管理员都有钥匙柜的总钥匙，但每次取用都会登记 | 简单、可恢复；符合“管理员可以给用户/组授权”的原始要求；离职或换人时不会卡死 | 管理员可以显式给自己授权；这不是“自动获得”，但仍是管理权限的延伸 |
| **B. 只有条目上传者（所有者）能管理授权** | 谁放进去，谁决定给谁看 | 权限边界更清楚；其他管理员不能改动 | 所有者离职/长期不可用时，授权容易卡住；需要额外恢复流程 |
| **C. 所有者管理授权，任意管理员可转移所有权** | 所有者管权限，但管理员能换锁 | 兼顾日常管理和交接 | 管理员仍可通过转移所有权获得访问；恢复路径更长 |

**推荐：A（任意管理员可以管理授权），并把所有授权变更写入安全日志。**

原因与边界：

- 原始需求就是“管理员可以选择用户组/用户并授权”；第一版管理员人数少、彼此可信。
- 管理员即使不自动获得内容，也可以显式给自己授权；这会被记录，而不是悄悄发生。
- 本项目的第 1 版仍是**服务器端加密**：服务器最高权限者本来就能接触密钥；应用层权限主要防止误看和普通用户越权，不能防住恶意服务器管理员。这个限制在可行性报告中已经说明。
- 如果你更希望“只有上传者能改授权”，可以选 B；代价是所有者不可用时的交接更麻烦。

### 3.5 已确定、无需再选的授权规则

- **有效权限 = 条目所有者，或直接授权给该用户，或该用户所在组被授权。** 三种来源取并集。
- 不设置“拒绝”规则；授权只有“有”或“没有”。
- 一个用户可以属于多个组；一个组可以访问多条内容。
- 把用户移出组、撤销组授权、撤销个人授权、停用账号后，下一次请求立即失效。
- 个人授权不会因为用户被移出组而自动取消。
- 条目所有者始终可以访问该条目；所有权只能由管理员转移给另一名启用的管理员。
- 管理员可以查看所有条目的**管理元数据**（标题、类型、授权情况），以便管理；但**不会因此自动获得内容解密权**（第 4 阶段执行内容权限）。
- 普通用户只能看到被授权的条目标题和必要信息；不能看到未授权条目，也不能直接猜 URL 访问。
- 管理员可以给自己授权，但会写日志；这是 v1 信任模型的边界。
- 第一版不做组嵌套、授权过期、拒绝规则和对外分享链接。

## 五、数据设计

### 5.1 新增数据对象

| 对象 | 需要记住什么 | 约束 |
|---|---|---|
| 用户组 | 名称、说明、创建人、创建/更新时间 | 名称唯一（去首尾空格）；名称 1–50 字 |
| 组成员 | 哪个组、哪个用户、谁加入、加入时间 | 同组同用户只能有一条；用户可属于多个组 |
| 内容条目 | 标题、类型（文件/文字）、说明、所有者、归档状态、时间 | 所有者必须是管理员；标题 1–120 字；本阶段不存真实内容 |
| 组授权 | 哪条条目、哪个组、授权人、时间 | 同一条目对同一组只能有一条 |
| 用户授权 | 哪条条目、哪个用户、授权人、时间 | 同一条目对同一用户只能有一条 |

### 5.2 关键规则

- 删除用户组前，若存在组授权：拒绝删除（HTTP 409），并返回受影响条目数量。
- 删除无授权的组：允许，同时删除组成员关系；已停用用户也可被移出组（管理员操作）。
- 删除用户：继续使用第 2 阶段的“停用”，不物理删除；停用后授权记录保留，但用户无法登录，也无法访问内容。
- 组授权和用户授权可以同时存在；有效权限取并集。
- 重复授权不新增记录；接口可返回已有授权（幂等）。
- 条目归档后，不出现在普通用户的可见列表；管理员可在归档列表恢复。
- 所有权转移目标必须是启用状态的管理员；转移后原所有者失去“所有者自动访问”，但仍可能通过组/个人授权保留访问。
- 本阶段条目不包含真实文件或文字秘密；第 4 阶段会增加加密内容字段/存储对象。

### 5.3 元数据与内容权限分开

- `can_view_metadata`：管理员、所有者或被授权的用户。
- `can_open_content`：所有者或被授权的用户；管理员若未获得所有者/授权，也不能内容访问。第 4 阶段会真正执行此函数；本阶段先在服务层和测试中定义。
- 普通用户访问未授权条目时返回 404，避免通过状态码探测条目是否存在。
- 管理员通过管理接口可以看到全部条目元数据，但不能用管理接口代替内容授权。

## 六、核心流程

### 6.1 创建用户组

1. 管理员进入“用户组”，点击“新建组”。
2. 填写名称、说明；保存。
3. 组出现在列表中；可以继续添加成员。

### 6.2 管理组成员

1. 管理员打开组的成员面板。
2. 选择一个启用中的用户加入组；可以一次加入多个。
3. 移出成员时立即生效；该用户通过这个组获得的所有内容访问权随之消失，但个人授权仍然保留。
4. 组页面显示“这个组当前能访问哪些条目”，便于授权前预览。

### 6.3 创建条目元数据（占位）

1. 管理员在“内容条目”页点击“新建条目”。
2. 填写标题、类型（文件/文字）、说明；不填写真实内容。
3. 创建者自动成为所有者。
4. 页面明确标注“本阶段为权限测试占位，真实内容将在第 4 阶段加入”。
5. 管理员可以归档占位条目；归档后普通用户看不到。

### 6.4 授权给用户组或单个用户

1. 管理员打开条目的授权面板。
2. 选择一个或多个组，和/或一个或多个用户。
3. 保存后立即生效。
4. 页面显示：
   - 所有者；
   - 组授权；
   - 用户授权；
   - 有效访问人预览（去重后的用户列表和数量）。
5. 重复添加同一组/用户不会产生重复记录。

### 6.5 普通用户查看被授权条目

1. 普通用户登录后进入“我的内容”。
2. 只看到被授权的条目元数据；看不到其他条目。
3. 打开条目详情时，占位内容显示“真实内容将在第 4 阶段加入”。
4. 任何未授权条目（包括直接改 URL）返回 404，而不是暴露“存在但无权”。

### 6.6 撤销授权

- 从条目移除组授权：该组所有成员立即失去这条内容的访问（个人授权仍有效）。
- 从条目移除用户授权：该用户立即失去访问（组授权仍有效）。
- 从组移除成员：该用户立即失去组授权带来的访问（个人授权仍有效）。
- 停用用户：立即无法登录，已有会话失效，权限不生效。
- 所有撤销都写安全日志。

### 6.7 转移所有权

1. 管理员在条目详情选择“转移所有权”。
2. 选择一个启用状态的管理员。
3. 确认后：新所有者获得所有者访问；原所有者失去“所有者自动访问”（除非另有授权）。
4. 写安全日志。
5. 本阶段不允许把所有权转给普通用户或停用账号。

### 6.8 删除用户组

1. 管理员点击删除。
2. 如果没有授权：确认后删除，组成员关系一并清理。
3. 如果有授权：拒绝删除，提示先撤销这些授权；列出受影响条目数量。
4. 写安全日志。

## 七、API 设计（初稿）

所有接口使用 `/api/v1/` 前缀；状态变更需要 CSRF，未登录返回 401，无权限返回 403。

### 7.1 管理员：用户组

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/groups/` | 分页、搜索组名/说明 |
| POST | `/api/v1/admin/groups/` | 创建组（名称、说明） |
| GET | `/api/v1/admin/groups/{id}/` | 组详情、成员、已授权条目数 |
| PATCH | `/api/v1/admin/groups/{id}/` | 修改名称/说明 |
| DELETE | `/api/v1/admin/groups/{id}/` | 删除组；有授权时返回 409 |
| POST | `/api/v1/admin/groups/{id}/members/` | 添加成员（一个或多个 user_id） |
| DELETE | `/api/v1/admin/groups/{id}/members/{user_id}/` | 移除成员 |

### 7.2 管理员：条目与授权

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/admin/items/` | 所有条目元数据，支持搜索、类型筛选、归档筛选 |
| POST | `/api/v1/admin/items/` | 创建占位条目（标题、类型、说明） |
| GET | `/api/v1/admin/items/{id}/` | 条目详情、授权、有效访问人预览 |
| PATCH | `/api/v1/admin/items/{id}/` | 修改标题/说明；类型创建后不可改 |
| POST | `/api/v1/admin/items/{id}/archive/` | 归档 |
| POST | `/api/v1/admin/items/{id}/unarchive/` | 恢复归档 |
| POST | `/api/v1/admin/items/{id}/owner/` | 转移所有权（目标必须是启用的管理员） |
| POST | `/api/v1/admin/items/{id}/grants/groups/` | 添加组授权（group_id） |
| DELETE | `/api/v1/admin/items/{id}/grants/groups/{group_id}/` | 移除组授权 |
| POST | `/api/v1/admin/items/{id}/grants/users/` | 添加用户授权（user_id） |
| DELETE | `/api/v1/admin/items/{id}/grants/users/{user_id}/` | 移除用户授权 |

### 7.3 普通用户：被授权条目

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/items/` | 仅返回当前用户被授权的活跃条目；分页、搜索 |
| GET | `/api/v1/items/{id}/` | 被授权条目的元数据；未授权返回 404 |

> 真实内容读取/下载接口在第 4 阶段增加；本阶段条目详情只返回元数据和“内容未实现”的说明。

### 7.4 响应规则

- 列表分页，默认每页 20 条。
- 组删除被拒绝：HTTP 409 + 受影响条目数量。
- 重复授权：不新建记录，返回幂等结果。
- 未授权普通用户访问条目：HTTP 404。
- 管理员接口对普通用户：HTTP 403。
- 所有响应不包含密码、密钥或真实内容。
- 组、成员、授权、所有权、归档操作写安全日志。

## 九、安全要求

| 编号 | 要求 | 说明 |

| S3-01 | 后端授权 | 每次列表/详情/授权请求都在后端判断，不依赖前端隐藏 |

| S3-05 | 个人授权独立 | 移出组不影响个人授权；撤销组不影响其他组 |

| S3-10 | 管理员边界 | 管理员接口需管理员角色；普通用户 403 |

### 信任模型说明

第 1 版服务器端加密下，管理员具备服务器层面的信任：管理员可以管理账号、重置密码，也可以显式给自己授权。应用层的“管理员不自动获得内容”主要防止**默认全量可见**和**普通用户越权**，不能防住恶意服务器管理员。若以后要求“连管理员也不能看”，需要第 4 阶段之后的端到端加密升级。

## 十三、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 迁移影响现有账号 | 用户无法登录/数据丢失 | 迁移前完整性检查 + 备份；只做新增表；迁移后对比账号和哈希；失败回滚 |
| 组授权过大 | 一批人意外看到内容 | 授权前显示组可访问条目和有效用户预览；写日志；撤销即时生效 |
| 管理员自授权/重置密码 | 权限边界被绕过 | 记录日志；在界面和文档说明 v1 信任模型；后续可升级端到端加密 |
| 删除组导致访问中断 | 普通用户突然看不到内容 | 本阶段采用“有授权禁止删除”，先撤销/转移 |
| 所有权人不可用 | 无法转移或管理条目 | 管理员可以转移给其他启用的管理员；写日志 |
| 未授权条目被枚举 | 泄露标题/存在性 | 服务端过滤查询；普通用户未授权直接返回 404 |
| 占位条目被误当真实内容 | 用户放入敏感信息 | 页面明确标注占位；不提供内容输入；文档提醒 |
| 权限缓存过期 | 撤销不即时 | 不使用长期权限缓存，每次请求查库/服务计算 |
| 查询/页面变慢 | 组多、授权多时列表慢 | 合理使用 `select_related/prefetch_related`、分页、索引；小团队优先 |
| 范围膨胀 | 本阶段难收尾 | 严格限制在组、元数据、授权；内容与加密放第 4 阶段 |

### 16.4 实现说明与差异

- API 同时接受批量字段 `user_ids` / `group_ids` 和单个字段 `user_id` / `group_id`；界面使用批量方式，方便一次选择多人或多个组。
- 管理员条目列表默认只显示活跃条目，可用 `archived=active|archived|all` 切换；普通用户始终看不到归档条目。
- 用户组说明最多 500 字，条目说明最多 1000 字；标题最多 120 字，组名最多 50 字。
- 条目类型创建后不可修改；本阶段没有真实内容字段。
- 有效访问人预览只统计**启用中的账号**。停用用户的授权记录保留，但重新启用前不生效。
- 任意管理员都可以编辑条目元数据和授权（D3-4 A）；管理员显式给自己授权会写日志，这是第 1 版服务器端加密的信任边界。
