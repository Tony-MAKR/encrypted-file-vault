## 一、文档目的与范围

### 1.1 目的

- 把你提出的需求整理成**可以逐条验收**的说明书。
- 明确角色、权限、业务流程、数据范围和不能做的事。
- 作为后续每个阶段 spec 和测试验收的依据。
- 本文档不涉及具体代码、框架和部署命令。

### 1.2 产品定义

一个**本地部署的加密文件与敏感信息管理系统**：

- 管理员负责建立用户、划分用户组、加密保存文件或文字秘密，并按组/按人授权。
- 普通用户只能看到并解密自己被授权的内容。
- 所有关键操作留痕，数据可备份、可恢复。
- 提供 Web 浏览器端和安装版应用端两种使用方式（应用端形态待确认）。

### 1.3 第一期目标

先在一个**可信的小范围环境**内跑通完整闭环：

1. 管理员能初始化系统、建账号、建组。
2. 管理员能上传文件，或保存网站/数据库等文字密码。
3. 内容加密落盘，脱离系统打不开。
4. 管理员能按组、按人授权，撤销后立即失效。
5. 被授权用户能登录、查看、解密。
6. 关键操作有审计记录，数据能备份和恢复。
7. 网页端和安装版客户端都能用（形态按 D1 确认）。

### 1.4 不在第一期范围

见第十一节。第一期不追求“大而全”，优先把**权限正确、加密可靠、数据不丢**做扎实。

## 二、用户角色与权限

### 2.1 角色定义

| 角色 | 通俗解释 | 主要职责 |
|---|---|---|
| 管理员 | 保险箱管理员 | 管账号、管组、管权限、上传内容、查看审计、备份恢复 |
| 普通用户 | 被授权的取件人 | 登录后查看/解密自己被授权的内容，管理自己的密码 |
| 未登录访客 | 站在门外的人 | 只能看到登录页，不能访问任何内容 |

> 第一版建议只保留这两种角色，不引入“部门管理员”“审计员”等复杂角色；后续确有需要再扩展。

### 2.2 权限矩阵（建议方案）

| 操作 | 管理员 | 普通用户 |
|---|---|---|
| 登录、退出、修改自己的密码 | 可以 | 可以 |
| 创建/停用普通用户 | 可以 | 不可以 |
| 创建/停用其他管理员 | 可以（且不能停用最后一个管理员） | 不可以 |
| 创建/修改/删除用户组 | 可以 | 不可以 |
| 增删组成员 | 可以 | 不可以 |
| 上传文件 / 新建文字条目 | 可以 | 不可以（第一期） |
| 修改条目标题、说明、标签 | 可以（限自己上传或获授权管理的条目） | 不可以 |
| 给条目授权 / 撤销授权 | 可以 | 不可以 |
| 查看自己上传的条目内容 | 可以 | 不适用 |
| 查看被授权的条目内容 | 仅在被明确授权时 | 仅在被明确授权时 |
| 查看审计日志 | 可以 | 不可以（第一期） |
| 系统设置、备份、恢复 | 可以 | 不可以 |
| 查看所有条目的**名称/授权情况**（不解密内容） | 可以（便于管理） | 不可以 |

### 2.3 管理员能否查看所有内容？——建议“默认不能”

这是本系统最重要的安全策略之一：

- **推荐策略**：管理员角色只代表“有管理权限”，**不等于自动拥有所有内容的解密权**。
  - 管理员可以查看所有条目的名称、类型、授权对象等管理信息，便于管理。
  - 但只有**该条目的上传者**，或**被明确授权的管理员**，才能解密内容。
  - 如果只有一个管理员，他就是所有内容的上传者，实际使用上没有区别。
- **另一种策略**：管理员天然可以解密所有内容。管理简单，但一旦管理员账号被盗，全部数据暴露；也与“只有被选择的组/人可以查看”的目标有冲突。
- **建议采用推荐策略**，并保留“所有权转移”功能：原上传者离职或账号停用时，可以把条目的管理权转给另一个管理员。

> 此项需要在阶段 1 前确认（见第十三节 Q5）。

### 2.4 普通用户的边界

- 不能自行注册；账号由管理员创建。
- 只能看到被授权的条目；**列表里连标题都不显示**给未授权者。
- 不能查看其他用户的账号、组、授权关系。
- 可以修改自己的登录密码。
- 第一版不提供普通用户上传/分享功能。

## 三、核心概念与关系

用生活化的方式理解：

- **用户**：一个可登录的人。
- **用户组**：若干用户的集合，例如“财务组”“运维组”。一个用户可以同时属于多个组。
- **条目**：系统里的一条受保护内容，只有两种类型：
  - **文件条目**：上传的一个文件（合同、证件、备份包等）。
  - **文字条目**：网站地址、账号、数据库密码、备注等文字信息。
- **授权**：规定“哪个组/哪个人”能看哪条内容。
- **审计记录**：谁在什么时候做了什么。
- **密文**：文件或文字加密后的乱码。
- **密钥**：解密用的钥匙。主密钥与密文分开存放。

关系一句话：**用户属于组；条目授权给组或人；用户通过组授权或个人授权获得访问权；所有访问都记录。**

## 四、核心业务流程

### 4.1 首次使用：初始化

1. 管理员安装/启动系统。
2. 进入初始化向导：设置站点名称、管理员账号和强密码。
3. 系统生成主密钥，保存在独立、受限制的位置。
4. 系统提醒管理员设置备份，并确认已妥善保存恢复材料。
5. 初始化完成后，管理员登录进入后台。

**关键要求**：初始化只能成功一次；已有数据时不能覆盖；中途失败可安全重试；不能把初始密码/密钥写进日志。

### 4.2 管理员建立用户和组

1. 管理员创建用户，设置初始密码，要求用户首次登录修改。
2. 管理员创建用户组，例如“财务组”。
3. 管理员把用户加入一个或多个组。
4. 所有创建、停用、移入/移出组操作都写入审计。

### 4.3 管理员保存文件或文字秘密

1. 管理员选择“上传文件”或“新建文字”。
2. 填写标题、说明、分类、标签等信息。
3. 上传文件或填写文字秘密。
4. 选择授权对象：
   - 一个或多个用户组；
   - 和/或一个或多个具体用户；
   - 可选“允许下载”（按 D5 的最终决定实现）。
5. 系统立即加密内容，保存密文和授权记录。
6. 管理员看到“已加密、已授权给哪些组/人”的确认信息。

### 4.4 普通用户查看和解密

1. 用户登录。
2. 首页只显示自己被授权的条目。
3. 打开文字条目：默认显示打码内容；点击“显示”后解密展示，可复制；操作记录审计。
4. 打开文件条目：在权限允许时，点击“下载/解密”获取原文件；操作记录审计。
5. 用户无法通过猜地址、改编号等方式访问未授权条目；服务器每次请求都校验权限。

### 4.5 撤销权限

1. 管理员把用户移出组，或取消某条授权，或停用账号。
2. 下一次请求立即失效，不需要等用户重新登录。
3. 撤销动作记录审计。
4. 已下载到用户电脑上的明文无法收回；系统通过留痕和制度约束。

### 4.6 备份与恢复

1. 管理员触发备份（后续可定时）。
2. 系统把数据库、密文文件、恢复所需密钥材料打包，用独立备份口令加密。
3. 备份文件存到管理员指定的位置；建议至少一份离线/异机保存。
4. 恢复时校验备份完整性和版本兼容性；禁止静默覆盖现有数据，必须先确认。
5. 恢复演练应写入运维文档。

## 七、数据需求

以下是“系统需要记住哪些信息”的通俗清单，不是最终数据库设计；具体字段在技术 spec 中确定。

### 7.1 主要数据对象

| 对象 | 需要记住什么 | 备注 |
|---|---|---|
| 用户 | 用户名、显示名、密码哈希、角色、状态、失败次数、锁定时间、创建时间 | 绝不保存明文密码 |
| 用户组 | 组名、说明、创建人、创建时间 | 组名唯一 |
| 组成员 | 哪个组包含哪个用户、加入时间 | 多对多 |
| 条目 | 类型（文件/文字）、标题、说明、分类、标签、上传者、状态、时间 | 标题等用于列表展示和搜索 |
| 文字密文 | 网址、账号、密码、备注的加密结果 | 只有授权者能解密 |
| 文件密文 | 存储位置、密文大小、校验值、加密后的原始文件名、文件类型 | 磁盘上用随机文件名 |
| 授权 | 哪条内容、授权给组还是人、对象编号、可查看/可下载、授权人、时间 | 组与个人授权取并集 |
| 审计日志 | 时间、操作者、动作、对象、IP、设备、结果 | 只追加，不提供修改 |
| 会话 | 哪个用户、何时登录、何时过期、何时最后活动 | 支持服务端强制失效 |
| 设置 | 站点名称、大小限制、超时、保留期等 | 不含密钥 |
| 备份记录 | 时间、位置、大小、结果、版本 | 用于运维排查 |
| 密钥材料 | 主密钥（独立文件，不在数据库明文）、每条内容的数据密钥（加密后保存） | 这是系统最关键的资产 |

### 7.2 数据完整性规则

- 用户被停用后不得登录，但其审计记录必须保留。
- 删除用户/组/条目采用“软删除 + 回收站”，避免误删造成不可逆损失。
- 删除用户组前提示受影响的条目和授权。
- 最后一名管理员不能被停用、删除或降级。
- 条目必须有至少一个上传者；所有权转移必须留痕。
- 授权对象必须是存在的组或用户；对象被删除后，相关授权失效但保留历史记录。
- 所有时间使用统一时区（建议北京时间）保存，界面按本地时区显示。
- 数据库结构变更必须通过迁移完成，不能直接改坏旧数据。

### 7.3 元数据与隐私说明

- **内容加密**：文件内容、文字秘密（网址/账号/密码/备注）必须加密。
- **标题、分类、标签**：为了列表和搜索，第一版可以明文保存；如果标题本身包含敏感信息，用户应避免写在标题里，或后续选择加密模式。
- **原始文件名**：建议加密保存，避免磁盘和备份中的文件名泄露。
- **日志**：不记录密码、文件内容、密钥；记录操作对象编号和必要的标题。
- **磁盘/备份**：建议开启 Windows BitLocker 等全盘加密，作为第二层保护。

## 八、非功能需求

### 8.1 安全需求（最高优先级）

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-S01 | 内容加密 | 文件和文字秘密使用 AES-256-GCM 等行业标准算法加密；使用成熟库，不自创算法 |
| NFR-S02 | 密钥保护 | 主密钥独立存放、权限受限；不写代码、不进数据库明文、不进日志、不通过网页静态目录暴露 |
| NFR-S03 | 密码保护 | 使用 Argon2id 等慢速哈希；不保存明文密码 |
| NFR-S04 | 传输安全 | 局域网/远程访问使用 HTTPS；禁止在不可信网络用明文 HTTP |
| NFR-S05 | 访问控制 | 默认拒绝；每次请求服务端校验；防止通过改 URL/编号越权 |
| NFR-S06 | 防暴力破解 | 登录限速、失败锁定、审计；后续支持双因素认证 |
| NFR-S07 | 防常见 Web 攻击 | 防跨站脚本、跨站请求伪造、注入、路径穿越、恶意上传 |
| NFR-S08 | 文件保护 | 密文目录不可通过网页直接访问；磁盘无原后缀；下载时逐次鉴权 |
| NFR-S09 | 完整性 | 加密数据带完整性校验；发现篡改/损坏拒绝返回 |
| NFR-S10 | 无明文泄露 | 服务器不落明文临时文件；日志/错误页不显示秘密；浏览器响应禁止缓存 |
| NFR-S11 | 会话安全 | 会话超时、退出即失效、敏感操作可要求重新验证身份 |
| NFR-S12 | 依赖安全 | 锁定依赖版本、扫描漏洞、及时更新；开源前移除密钥和真实数据 |
| NFR-S13 | 最小权限 | 服务器进程、数据目录、数据库账号都按最小权限运行 |
| NFR-S14 | 备份安全 | 备份必须加密；备份口令与数据分开保管 |
| NFR-S15 | 审计 | 关键操作可追溯；审计日志不提供界面修改/删除 |

**威胁模型（第一版）**：

- 要防：未登录者、内部未被授权者、偷走硬盘/备份的人、网络窃听者、暴力破解者、误授权操作。
- 不承诺防：拥有服务器最高权限的恶意管理员、已被植入木马/键盘记录器的终端、授权用户主动拍照外传、物理胁迫。
- 如果“管理员也不可信”是硬要求，请选端到端加密（D3 选项 B）。

### 8.2 性能需求

第一版按“小团队、单机、局域网”设计，建议目标如下（可在阶段 1 调整）：

- 账号数量：50 个以内。
- 同时在线：10 人左右。
- 条目数量：10,000 条以内仍可流畅列表/搜索。
- 单文件默认上限：200 MB，可由管理员调整；大文件必须流式处理，不能爆内存。
- 列表/搜索响应：正常数据量下 2 秒内。
- 上传/下载速度：主要受磁盘和局域网带宽限制，不做额外压缩。
- 磁盘写满、文件损坏、加密失败时必须明确报错，不能留下“看似成功”的坏数据。

> 如果用户数、文件大小或并发量远超以上范围，需要提前说明，可能需要更强的数据库/存储方案或云端部署。

### 8.3 可用性与可靠性

- 第一版是单台主机，**不承诺高可用**；主机停机则服务不可用。
- 建议使用 UPS，降低突然断电风险。
- 默认每天备份一次；重要操作前可手动备份。
- 恢复目标：优先保证数据可恢复；恢复时间取决于数据量和备份位置。
- 磁盘空间不足时提前告警，并拒绝新的上传，避免写坏已有数据。
- 升级前自动备份；升级失败可回滚到旧版本和数据。

### 8.4 易用性

- 全中文界面，术语尽量用“保险箱、钥匙、授权”等直白说法。
- 管理员首次使用有引导；危险操作有明确后果说明。
- 普通用户最多三次点击就能看到被授权内容。
- 支持常见桌面浏览器和手机浏览器；应用端按 D1 的形态适配。
- 表单错误提示具体到字段，告诉用户怎么改。

### 8.5 兼容性

- Web 端：Chrome、Edge、Firefox、Safari 的较新版本。
- 服务器：优先 Windows 10/11；后续可支持 Linux。
- 应用端：按 D1 确认后确定 Windows/macOS/Android/iOS 范围。
- 文件类型：不依赖本机 Office/播放器；加密下载不要求服务器安装对应软件。
- 不建议支持 IE 等已停止维护的浏览器。

### 8.6 可维护性与开源

- 代码、配置、文档分离；提供配置样例，不提交真实密钥。
- 数据库结构有版本号和迁移脚本。
- 关键逻辑有自动化测试；每个阶段有验收清单。
- 日志分级、可读、可排障，但不泄露秘密。
- 提供 README、部署说明、备份恢复说明、安全策略、贡献指南。
- 依赖许可证兼容；开源前做一次密钥/隐私扫描。
- 版本号使用语义化版本（如 1.0.0），升级说明写清不兼容变更。

### 8.7 隐私与合规

- 只收集业务必需的数据（账号、条目、审计）。
- 审计日志保留期可配置；到期清理需留痕。
- 用户停用/删除后的数据处理规则需明确；审计记录通常需要保留。
- 若用于公司业务、对外服务或涉及个人信息，应评估《网络安全法》《数据安全法》《个人信息保护法》及商用密码相关规定；必要时咨询法律/合规专业人士。
- 开源许可证是法律选择，建议在发布前单独确认（宽松许可证 vs AGPL）。
- 本文档不构成法律意见。

## 九、验收标准

以下场景用于判断第一版“是否真的做完了”。每条都应能在测试中演示。

### 9.1 核心功能

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-01 | 首次初始化 | 能创建第一个管理员，生成密钥，进入系统；重复初始化被拒绝且不覆盖数据 |
| AC-02 | 创建用户和组 | 管理员能建用户、建组、把用户加入多个组；普通用户无法进入管理页面 |
| AC-03 | 上传文件 | 文件上传成功；服务器磁盘上找不到原文件名的明文文件；用常见软件双击无法打开 |
| AC-04 | 保存文字秘密 | 网站/账号/密码/备注保存成功；密码默认打码；刷新后仍能正确解密 |
| AC-05 | 按组授权 | 组内用户能在列表看到并解密；组外用户看不到，直接访问接口也被拒绝 |
| AC-06 | 按人授权 | 被单独授权的用户能访问；未被授权者不能访问 |
| AC-07 | 撤销授权 | 移出组/取消授权后，下一次请求立即失败；不需要等重新登录 |
| AC-08 | 个人授权与组授权并存 | 取消组授权后，个人授权仍然有效；反之亦然 |
| AC-09 | 未授权访问 | 改 URL/编号/接口参数都无法访问他人内容；返回统一错误，不泄露是否存在 |
| AC-10 | 下载留痕 | 下载文件/复制密码都生成审计记录；记录中没有密码/文件内容 |
| AC-11 | 文件完整性 | 手动篡改密文后，系统拒绝下载并提示损坏；正常文件校验通过 |
| AC-12 | 删除与恢复 | 删除进回收站；可恢复；永久删除需二次确认和重新验证；记录审计 |
| AC-13 | 最后一名管理员保护 | 无法停用/删除/降级最后一名管理员 |
| AC-14 | 登录保护 | 连续输错密码达到阈值后锁定；锁定期内正确密码也不能登录；审计有记录 |
| AC-15 | 会话失效 | 退出后旧会话不能再访问；超时后要求重新登录；停用账号立即踢下线 |
| AC-16 | 应用端 | 应用端能登录、看到相同的授权内容、下载/复制；未授权内容同样不可见 |

### 9.2 备份与恢复

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-17 | 备份 | 能生成加密备份；备份文件不能用普通工具直接读出内容 |
| AC-18 | 恢复 | 在空环境用“备份 + 正确口令”完整恢复用户、组、条目、授权和密文 |
| AC-19 | 错误口令 | 错误口令无法恢复，且不会破坏现有数据 |
| AC-20 | 恢复确认 | 恢复前必须明确确认，不能静默覆盖现有数据 |
| AC-21 | 版本兼容 | 旧版本备份在新版本上的处理有明确提示；不兼容时拒绝并说明 |

### 9.3 安全与质量

| 编号 | 场景 | 通过标准 |
|---|---|---|
| AC-22 | 日志脱敏 | 日志、错误页、浏览器控制台中找不到明文密码、密钥、文件内容 |
| AC-23 | 路径穿越 | 构造 `../` 等恶意文件名无法写到数据目录之外 |
| AC-24 | 大文件 | 上传/下载大文件时内存占用可控，服务器不生成明文临时文件 |
| AC-25 | 磁盘写满 | 磁盘空间不足时上传失败且已有数据不受损，提示清晰 |
| AC-26 | HTTPS | 局域网访问启用 HTTPS；安全 Cookie 生效；混合内容被阻止 |
| AC-27 | 权限矩阵 | 逐条验证管理员/普通用户权限，普通用户不能调用管理接口 |
| AC-28 | 审计边界 | 审计日志界面不能修改/删除；清理过期日志有系统记录 |

## 十、约束与假设

1. **单机部署**：第一版运行在一台常开的 Windows 电脑/服务器上；不做多机集群。
2. **局域网优先**：默认用户在同一个网络内访问；公网访问需额外安全设计，不在第一版。
3. **管理员可信**：第一版采用服务器端加密，信任服务器管理员；如果要防管理员，选端到端加密。
4. **管理员人数少**：建议 1–2 名管理员；多管理员的所有权/权限策略在阶段 3 细化。
5. **普通用户不上传**：内容由管理员上传/创建；后续再考虑用户投稿。
6. **文件主要靠下载使用**：第一版不做 Office/PDF 在线预览和编辑。
7. **备份是硬要求**：没有备份就不算可交付；主密钥/备份口令丢失视为数据丢失。
8. **网络与硬件由你提供**：主机、硬盘、网络、UPS、固定 IP 等由你准备；软件负责正确使用它们。
9. **法律合规需专业确认**：若用于商业/对外服务，请咨询法律专业人士；本方案不构成法律意见。
10. **需求会变化**：每个阶段开始前通过 spec 锁定范围；新增需求进入后续版本，避免无限扩大第一版。

## 十一、第一期明确不做

以下内容不是永远不做，而是**不放进第一版**，避免拖慢核心闭环：

- 云端对象存储、多租户 SaaS、跨组织共享。
- 原生手机 App（除非 D1 选 B/C；即便如此也建议分阶段）。
- 公开注册、邀请链接、对外分享链接。
- 单点登录（LDAP/AD/OAuth）、企业微信/钉钉集成。
- Office/PDF 在线预览、在线编辑、全文检索文件内容、OCR。
- 文件水印、防截屏、防打印、数字版权管理（DRM）。
- 双因素认证、硬件安全密钥、生物识别（后续）。
- 条目版本历史、自动过期、定时发布。
- 多管理员分级（超级管理员/审计员）、细粒度自定义角色。
- 高可用、负载均衡、多机备份、异地容灾。
- 与杀毒引擎集成、文件内容病毒扫描。
- 移动端离线缓存、桌面端离线模式。
- 计费、套餐、用户自助购买。

> 如果其中某项对你来说是“第一版必须有”，请现在提出，我会重新评估范围和阶段。

## 十四、术语小抄

| 名词 | 大白话 |
|---|---|
| P0 / P1 / P2 | 第一版必须做 / 尽量做 / 以后做 |
| 条目 | 系统里的一条受保护内容，可能是文件，也可能是文字密码 |
| 授权 | 允许某个组或某个人访问某条内容 |
| 撤销 | 收回已经给出的访问权，下一次请求立即失效 |
| 软删除 | 先放进回收站，不立刻从磁盘彻底删除 |
| 密文 | 加密后的乱码，没有钥匙打不开 |
| 数据密钥 | 每条内容各自的一把小钥匙，用来加密该内容 |
| 主密钥 | 用来锁住所有小钥匙的总钥匙 |
| 备份口令 | 专门保护备份包的密码；和登录密码不是一回事 |
| 审计日志 | 谁、在什么时候、做了什么操作的记录 |
| 会话 | 从登录到退出/超时之间的一段登录状态 |
| 应用端 | 安装后使用的客户端；具体是电脑还是手机，待 D1 确认 |
| 端到端加密 | 内容在用户设备上就加密，服务器只存密文，连管理员也打不开 |
| 迁移 | 升级时把旧数据结构安全地转换成新结构，不丢数据 |
| spec | 每个阶段开工前写清楚“做什么、怎么验收”的规格说明 |
